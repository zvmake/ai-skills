# Источники истины для код-ревью (универсальный порядок поиска)

Справочник для Шага 2 `SKILL.md`. Скилл не предполагает конкретной структуры документации: источники требований и стандартов обнаруживаются в репозитории и в контексте запроса. Ниже — где искать, как разрешать конфликты и что делать при отсутствии источников.

Поиск выполняй встроенными инструментами агента (`glob` / `grep` / `read` или аналоги) с исключением каталогов зависимостей, сборки и VCS. Читай только файлы, относящиеся к затронутым модулям и общим правилам; не загружай в контекст всю документацию репозитория.

---

## 1. Регламенты процесса проекта (читать первыми)

Инструкции для ИИ-агентов и разработчиков могут переопределять поведение ревью: где лежат ТЗ и контракты модулей, какие каталоги являются служебными и не входят в скоуп, какой формат отчёта обязателен, как маркировать замечания. Найди и прочитай их до сбора остальных источников.

- Инструкции для ИИ-агентов: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` или аналогах, в зависимости от вашего проекта — в корне и в каталогах затронутых модулей (вложенные файлы уточняют корневые).
- Правила участия и ревью: `CONTRIBUTING*`, `CODE_REVIEW*`, `REVIEWING*`, `.github/pull_request_template.md`, `CODEOWNERS` или аналоги.
- Базы знаний проекта и агентов (если есть): каталоги вида `.memory/`, `memory-bank/`, `.ai/`, `.docs/`, `docs/` или аналоги — структуру и назначение файлов определяй по их индексу/README, а не по догадке.

Если регламент проекта задаёт расположение ТЗ, контрактов модулей, сквозных паттернов, схемы БД или формат отчётности — используй именно его, а разделы ниже применяй как дополнение.

## 2. Источники оси `Spec & Contracts`

| Источник | Где искать |
|---|---|
| Требования текущего запроса | сообщение пользователя или вызывающего агента, приложенные файлы и ссылки |
| Описание задачи / issue / PR / MR | текст в запросе; если доступен CLI трекера — только читающие команды (например, `gh pr view`, `gh issue view`, `glab mr view`) |
| Файлы задач и спецификации | каталоги задач/спецификаций, указанные в регламенте проекта; `docs/**`, `spec*/**`, `requirements*` |
| Архитектурные решения | `docs/adr/**`, `adr/**`, `docs/decisions/**`, `ARCHITECTURE*` |
| Контракты API и сообщений | `openapi.*`, `swagger.*`, `*.graphql` / `schema.graphql`, `*.proto`, `*.schema.json`, `asyncapi.*`, `*.avsc` |
| Схема данных | миграции (`migrations/`, `db/migrate/`, `alembic/`, ресурсы Flyway / Liquibase), схемы ORM (например, `schema.prisma`, модели/сущности), документы со схемой БД |
| Публичные типы / DTO | общие пакеты контрактов, каталоги `contracts/`, `shared/`, `types/`, `dto/` и аналоги, определяемые по импортам изменённого кода |
| Заявленное намерение изменений | заголовок и описание PR/MR, сообщения коммитов (`git log <base>..HEAD`) |

## 3. Источники оси `Architecture, Reliability & Standards`

| Источник | Где искать |
|---|---|
| Стандарты кодирования и архитектуры | `CODING_STANDARDS*`, `STYLEGUIDE*`, `*GUIDELINES*`, `CONVENTIONS*`, `ARCHITECTURE*`, разделы `docs/**`, на которые ссылаются инструкции из п. 1 |
| Сквозные паттерны и каноны проекта | каталоги паттернов/канонов, указанные в регламенте проекта |
| Конфигурации линтеров, форматтеров, тайпчекеров | `eslint.config.*`, `.eslintrc*`, `biome.json*`, `.prettierrc*`, `tsconfig*.json`; `pyproject.toml` (`[tool.ruff]`, `[tool.mypy]`, `[tool.black]`), `setup.cfg`, `.flake8`, `mypy.ini`; `checkstyle*.xml`, `detekt*.yml`; `.editorconfig`, `Directory.Build.props`, `.globalconfig`; `.golangci.y*ml`; `rustfmt.toml`, `clippy.toml`; `phpstan.neon*`, `psalm.xml`, `phpcs.xml*`; `.rubocop.yml` |
| Правила границ модулей | `.dependency-cruiser.*`, правила `eslint-plugin-boundaries` / `@nx/enforce-module-boundaries`, ArchUnit-тесты, `.importlinter`, NetArchTest-тесты, `.go-arch-lint.yml`, `deptrac.yaml`, `packwerk.yml` |
| Пороги и гейты качества | конфигурация CI (`.github/workflows/**`, `.gitlab-ci.yml` и аналоги), пороги покрытия в конфигурации тестового раннера |

Что включено в линтер/форматтер/тайпчекер и реально запускается в CI — вручную не дублируется (правило 4 `SKILL.md`). Что выключено в их конфигурации — не выставляется как нарушение стандарта проекта, но может быть замечанием по существу (например, отключённая проверка, скрывающая реальный дефект).

## 4. Приоритет источников при конфликте

1. Явные указания пользователя в текущем запросе (скоуп ревью, база сравнения, фокус проверки).
2. Требования задачи и согласованные контракты (ТЗ, спецификация, API-контракты, схема БД).
3. Документированные регламенты, стандарты и паттерны проекта.
4. Идиомы языка/фреймворка и общепринятые практики (чек-лист `SKILL.md`, `references/stack-matrix.md`).

Если источники одного уровня противоречат друг другу или требование ведёт к дефекту (гонка, потеря данных, нарушение безопасности) — это замечание с источником `дефект требований/стандарта`, а не повод молча выбрать одну из трактовок.

## 5. Отсутствие источников

| Ситуация | Действие | Пометка в отчёте |
|---|---|---|
| Требования не переданы и не найдены | Ось 1 проверяется по заявленному намерению (PR/MR, коммиты) и внутренней согласованности изменений | «требования не переданы (проверено по заявленному намерению)» |
| Нет ни требований, ни описания намерения | задай пользователю вопрос о цели изменений; если ответа нет — Ось 1 ограничивается обратной совместимостью и целостностью швов | то же + перечень непроверенного |
| Стандарты проекта не найдены | Ось 2 проверяется по чек-листу `SKILL.md` и идиомам стека | «стандарты не найдены (общепринятые практики)» |
| Ссылка на документ есть, но файл недоступен | не восстанавливай содержимое по догадке | вердикт `PENDING` или замечание с перечнем недостающих данных |
