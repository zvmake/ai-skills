# OWASP Top 10 — детальные тест-кейсы (динамика + статика)

Для каждой категории: что искать в коде (SAST) и как подтвердить на запущенном приложении (DAST). Готовые пейлоады бери из `payloads.md`.

## A01: Broken Access Control (IDOR / BOLA / BFLA / Cross-Tenant / привилегии)

**Что искать в коде**
- Эндпоинты без middleware/guard проверки прав; `id`/`userId`/`tenantId` из параметров пути, query, заголовков или тела запроса без сверки с владельцем и организацией из сессии/токена.
- Роли и права проверяются только на клиенте (роутер SPA, скрытие элементов UI), а сервер выполняет запрос без собственной проверки.

**Как подтвердить**
1. Создай двух пользователей (A и B, а для B2B/SaaS — также две разные организации/тенанта). Создай от лица B тестовый ресурс (`{B_id}`). Залогинься как A.
2. Запроси ресурс B от лица A: `GET /api/items/{B_id}` с токеном A.
3. Если ответ вернул данные B — IDOR подтверждён.
4. Повтори для мутаций (`PATCH/PUT/DELETE /api/items/{B_id}` — удаление проверяй только на специально созданном тестовом объекте `{B_id}`, чтобы не повредить существующие данные стенда) и для списков/поиска/экспорта с подменой `tenantId` / `organizationId`.
5. Для ролей: пользователь с ролью `user` пробует административный маршрут или операцию — `/api/admin/users`.
6. Попробуй вызвать приватный эндпоинт вообще без токена и с неверным/просроченным токеном.

## A02: Cryptographic Failures

- JWT без срока/алгоритма, слабый `secret`, передача паролей/токенов без TLS.
- Подтверди: раскодируй JWT (base64), проверь `alg`, `exp`; при `alg=none` попробуй подписать самодельный токен (только на своём приложении).

### JWT — углублённые атаки (всегда проверять, если используется JWT)

- **`alg=none`**: измени header на `{"alg":"none","typ":"JWT"}`, убери подпись (третий сегмент пустой или отсутствует) — проверь, принимает ли сервер токен. Пейлоад и шаги — в `payloads.md`.
- **RS256 → HS256 key confusion**: если сервер поддерживает оба алгоритма, подпиши токен алгоритмом `HS256`, используя публичный RSA-ключ (обычно доступен через `/.well-known/jwks.json` или в сертификате) как HMAC-секрет. Если сервер верифицирует без строгой проверки `alg`, токен пройдёт.
- **`kid`-injection**: если в header есть `kid` (key ID) и сервер подгружает ключ по этому полю (например, читает файл/URL) — попробуй path traversal (`kid: "../../../../dev/null"`, известный как атака на `kid` → пустой ключ) или SQL-инъекцию, если `kid` идёт в запрос к БД.
- **Слабый/угадываемый secret**: если `alg=HS256`, попробуй брутфорс секрета по словарю (`hashcat -m 16500` offline, без нагрузки на сервер) — частая находка: `secret`, `changeme`, название проекта.
- **Отсутствие проверки `aud`/`iss`**: токен, выпущенный для другого клиента/сервиса, принимается текущим API. Проверь, валидирует ли сервер `audience`/`issuer`, а не только подпись и `exp`.
- **`exp` в далёком будущем / отсутствует**: раскодируй payload, проверь срок жизни токена; чрезмерно долгоживущие access-токены — риск при утечке.

### OAuth2 / OIDC / SSO (проверять всегда, если есть внешняя авторизация — Google/GitHub/корпоративный IdP)

**Что искать в коде**
- Валидация `redirect_uri`/`callback URL`: точное совпадение со списком (whitelist) vs проверка через `startsWith`/подстроку/regex — последнее почти всегда обходится.
- Наличие и проверка `state` (защита от CSRF в OAuth-флоу) и `PKCE` (`code_verifier`/`code_challenge`) для публичных клиентов.
- Проверка подписи и `nonce` в `id_token` (OIDC) — не просто декодирование без верификации.
- Куда пишутся токены после обмена (`access_token`, `refresh_token`) — localStorage vs httpOnly cookie; попадают ли в URL (query string) и, соответственно, в логи/`Referer`/историю браузера.

**Как подтвердить**
1. Замени `redirect_uri` на домен, похожий на легитимный, но контролируемый тобой (`{протокол}://{домен}.evil.example`, `{протокол}://{домен}@evil.example`, добавление `/../evil`) — проверь, принимает ли authorization server.
2. Убери или замени параметр `state` в запросе на авторизацию — проверь, требует ли callback-эндпоинт его совпадения.
3. Если используется `code` flow без PKCE для публичного клиента (SPA/мобильное приложение) — попробуй перехватить/повторно использовать `authorization code` (code reuse) от другого сеанса.
4. Проверь, не попадает ли `access_token`/`code` в `Referer`-заголовок при переходе со страницы callback на сторонний ресурс (картинки/скрипты с внешних доменов).
5. Для id_token: подмени payload без пересчёта подписи — должен быть отклонён; если используется `alg=none` в id_token — тот же тест, что и для обычного JWT.

## A03: Injection (SQL / NoSQL / Command)

**SQL**
- В коде ищи сырые SQL-запросы и места конкатенации/интерполяции строк в запросах к БД (см. матрицу конструкций в `attack-surface.md`).
- Динамически: в параметр подставь `' OR '1'='1` и варианты с комментарием `--`; сравни ответы (разные наборы данных / ошибки 500 / раскрытие структуры). Признак инъекции — поведение меняется от полезной нагрузки, а не только от валидных данных.

**NoSQL и ORM Operator Injection**
- Если используется Mongo-подобный слой или ORM, принимающий вложенные фильтры (Prisma, Sequelize, Django ORM): отправь в JSON-тело объект-оператор `{"$ne": null}` / `{"not": null}` / `{"startsWith": ""}` вместо ожидаемой строки (например, в поле `password` или `resetToken`) и проверь, не обходится ли условие выборки.

**Command**
- Параметры, попадающие в вызовы командной оболочки ОС (см. матрицу конструкций в `attack-surface.md`): проверь инъекцию через `;`, `&&`, `$(...)`, обратные кавычки (см. `payloads.md`).

## A04: Insecure Design

- Логика сброса пароля без второго фактора, неограниченные попытки, раскрытие существования аккаунта (user enumeration).
- Подтверди: разница ответа на «существующий/несуществующий» email при login/register/recovery (по коду ответа, тексту или времени).

## A05: Security Misconfiguration

- Разрешение произвольного `Origin` в CORS (включая `*`, `Origin: null` и ошибки префикса/суффикса/неэкранированной точки в regex) при `Access-Control-Allow-Credentials: true`, отсутствие `HttpOnly`/`Secure`/`SameSite` на сессионных cookie, отсутствие `Content-Security-Policy` (`frame-ancestors`), `Strict-Transport-Security` (HSTS), `X-Content-Type-Options: nosniff`, `Referrer-Policy`, отсутствие `Cache-Control: no-store` на ответах с приватными данными, раскрытие stack trace и внутренней структуры в ответах 500, включённый debug-режим в production.
- Подтверди: `curl -I` к API — смотри заголовки и `Set-Cookie`; проверь заголовки ответа с `Origin: https://evil.example`, `Origin: https://{домен}.evil.example` и `Origin: null`; отправь невалидный JSON — проверь, не утекает ли stack trace и внутренние пути.

## A06: Vulnerable and Outdated Components (Supply Chain)

- Проверка зависимостей штатным SCA-инструментом стека (`npm audit` / `pnpm audit`, `pip-audit` / `safety`, `govulncheck`, `mvn dependency-check:check`, `dotnet list package --vulnerable`, `composer audit`, `bundle audit`), устаревшие версии пакетов и наличие lock-файла.

## A07: Identification and Authentication Failures

- Перебор логина/OTP без rate limit, слабая политика паролей, `JWT` без `exp`, хранение refresh-токена в `localStorage`, отсутствие инвалидации старых сессий/токенов при выходе и смене пароля, многоразовые или долгоживущие токены сброса пароля, утечка токена сброса через `Referer`.
- Подтверди: несколько неудачных логинов подряд — блокируется ли; остаётся ли старый токен/сессия рабочим после logout или смены пароля; можно ли повторно использовать ссылку сброса пароля.

## A08: Software and Data Integrity Failures

- Небезопасная десериализация недоверенных данных, отсутствие проверки криптографической подписи входящих вебхуков, отсутствие проверки целостности зависимостей (lockfile, SRI для внешних скриптов).

## A09: Security Logging and Monitoring Failures

- Логирование паролей, токенов, ключей или ПДн в стандартный вывод или файлы логов; отсутствие записи критичных событий безопасности (вход, ошибки авторизации, смена прав).

## A10: Server-Side Request Forgery (SSRF)

- URL/адрес из пользовательского ввода передаётся в серверный HTTP-клиент (см. `attack-surface.md`).
- Подтверди: передай `http://127.0.0.1:{порт}`, `http://169.254.169.254/latest/meta-data/`, `http://[::1]`, `http://localhost` и проверь, выполняется ли запрос к внутреннему ресурсу (по времени ответа/контенту), а также обход через HTTP-редирект. Используй свой коллбэк-эндпоинт или локальный listener, чтобы увидеть факт обращения.

## Соответствие OWASP API Security Top 10

Если в приложении есть HTTP/REST/GraphQL API, наравне с обычным OWASP Top 10 сверяйся с [OWASP API Security Top 10](https://owasp.org/API-Security/), где часть категорий сформулирована точнее для API:

| API Top 10 | Соответствие / уточнение | Что проверить дополнительно |
|---|---|---|
| API1: Broken Object Level Authorization | = IDOR/BOLA (A01) | см. раздел A01 выше |
| API2: Broken Authentication | = A07 | см. раздел A07 и JWT/OAuth deep-dive выше |
| API3: Broken Object Property Level Authorization | Excessive Data Exposure + Mass Assignment | Проверь, не возвращает ли API поля, которые не нужны клиенту (`password`, `internalNotes`, чужие связи) — фильтрация должна быть на сервере (явный выбор полей / выходная схема), а не «фронт просто не показывает». Проверь Mass Assignment: отправь в теле запроса лишние поля (`role: "admin"`, `isVerified: true`, `balance: 999999`, `tenantId: "..."`) при регистрации/обновлении профиля — применяются ли они без фильтрации по белому списку полей. |
| API4: Unrestricted Resource Consumption | = Rate limiting/DoS, но шире | Лимиты не только на auth-эндпоинты, но и на дорогие операции (экспорт, поиск, генерация отчётов, загрузка больших файлов), лимиты на размер массивов в теле запроса (pagination abuse — `?limit=999999`). |
| API5: Broken Function Level Authorization | = BFLA, часть A01 | Проверь доступ к admin-функциям через изменение метода/версии эндпоинта, не только через явный `/admin` путь. |
| API6: Unrestricted Access to Sensitive Business Flows | Бизнес-логика | Доступна ли критичная бизнес-операция (покупка, перевод, регистрация) без ограничений — автоматизация ботом, обход капчи/подтверждения. |
| API7: Server Side Request Forgery | = A10 | см. раздел A10 выше |
| API8: Security Misconfiguration | = A05 | см. раздел A05 выше |
| API9: Improper Inventory Management | Устаревшие/недокументированные версии API | Проверь наличие старых версий (`/api/v1/` рядом с `/api/v2/`), забытых debug/internal эндпоинтов, staging-окружений, доступных снаружи. |
| API10: Unsafe Consumption of APIs | Доверие к сторонним API | Если приложение вызывает внешние API и доверяет их ответам без валидации (внедрение через ответ третьей стороны) — отдельный вектор, особенно при webhook-приёме данных от внешних сервисов. |

## Детализация сквозных веб-уязвимостей (XSS, CSRF, Загрузка файлов, Rate Limiting)

Эти классы уязвимостей входят в категории OWASP Top 10 (`XSS → A03 Injection`, `CSRF и Path Traversal → A01 Broken Access Control`, `File Upload и Rate Limiting → A04 Insecure Design / API4`) и проверяются на каждом веб-приложении:

### XSS (reflected / stored / DOM)
- **Код**: отключение автоэкранирования шаблонизатора/фреймворка (`dangerouslySetInnerHTML`, `bypassSecurityTrustHtml`, `v-html`, `|safe`, `th:utext`, `@Html.Raw`, `{!! !!}`) или прямая запись в `innerHTML`/`document.write` без санитизации (`DOMPurify`); отражение ввода в ответе без кодирования.
- **Reflected**: в параметр подставь `<script>alert(document.domain)</script>` (или простой `<img src=x onerror=...>`) и проверь, попал ли в HTML-ответ без кодирования.
- **Stored**: сохрани пейлоад через форму/профиль и открой страницу, где он рендерится — сработал ли.
- **DOM**: пейлоад попадает в JS-контекст (`location.hash`, `location.search`, `postMessage`) и вставляется в DOM без санитизации.
- Полезная нагрузка берётся из `payloads.md`; фиксируй, экранируется ли ввод (`&lt;script&gt;`).

### CSRF
- Мутирующие запросы с cookie-аутентификацией без `SameSite` и без CSRF-токена, либо приём JSON-эндпоинтом запросов с `Content-Type: text/plain` / `application/x-www-form-urlencoded` (обход CORS preflight).
- Подтверди: проверь `Set-Cookie` на `SameSite`, `HttpOnly`, `Secure`; если сессия передаётся в cookie и нет анти-CSRF токена или строгой проверки `Origin`/`Content-Type: application/json` — приведи PoC-форму (HTML) как доказательство.

### File Upload / Path Traversal / Zip Slip
- Загрузка без проверки расширения и реального содержимого (magic bytes), исполнение загруженного файла на сервере или в браузере (`.html`/`.svg` без `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`); чтение/запись файлов по пользовательскому пути; распаковка архивов без проверки путей вхождения (`../` или `..\` внутри zip/tar — Zip Slip).
- Подтверди: загрузи тестовый `.html`/`.svg`; подставь `../../etc/passwd` (Linux/macOS), `..\..\Windows\win.ini` (Windows) или `..%2f..%2f` в файловый параметр.

### Rate Limiting / DoS
- Отсутствие лимитов на auth-эндпоинтах, большие payload.
- Подтверди: N запросов подряд без задержки/блокировки.

## Как оформлять результат
Каждую подтверждённую находку веди по шаблону отчёта (см. SKILL.md, Фаза 4) с PoC-запросом, ожидаемым/фактическим ответом и местом в коде (для gray-box).
