# OWASP Top 10 — детальные тест-кейсы (динамика + статика)

Для каждой категории: что искать в коде (SAST) и как подтвердить на запущенном приложении (DAST). Готовые пейлоады бери из `payloads.md`.

## A01: Broken Access Control (IDOR / BOLA / BFLA / привилегии)

**Что искать в коде**
- Эндпоинты без guard; `id`/`userId` из `@Param`/`@Query` без сверки с владельцем из токена.
- Роли/права проверяются только на клиенте (Angular `canActivate`), а сервер доверяет всем.

**Как подтвердить**
1. Создай двух пользователей (A и B). Залогинься как A.
2. Возьми ресурс, принадлежащий B (по `id`), и запроси его от лица A: `GET /api/items/{B_id}` с токеном A.
3. Если ответ вернул данные B — IDOR подтверждён.
4. Повтори для мутаций: `PATCH/DELETE /api/items/{B_id}` от A.
5. Для ролей: пользователь с ролью `user` пробует эндпоинт `admin` — `/api/admin/users`.
6. Попробуй вызвать приватный эндпоинт вообще без токена и с неверным токеном.

## A02: Cryptographic Failures

- JWT без срока/алгоритма, слабый `secret`, передача паролей/токенов без TLS.
- Подтверди: раскодируй JWT (base64), проверь `alg`, `exp`; при `alg=none` попробуй подписать самодельный токен (только на своём приложении).

### JWT — углублённые атаки (всегда проверять, если используется JWT)

- **`alg=none`**: измени header на `{"alg":"none","typ":"JWT"}`, убери подпись (третий сегмент пустой или отсутствует) — проверь, принимает ли сервер токен. Пейлоад и шаги — в `payloads.md`.
- **RS256 → HS256 key confusion**: если сервер поддерживает оба алгоритма, подпиши токен алгоритмом `HS256`, используя публичный RSA-ключ (обычно доступен через `/.well-known/jwks.json` или в сертификате) как HMAC-секрет. Если сервер верифицирует без строгой проверки `alg`, токен пройдёт.
- **`kid`-injection**: если в header есть `kid` (key ID) и сервер подгружает ключ по этому полю (например, читает файл/URL) — попробуй path traversal (`kid: "../../../../dev/null"`, известный как atакa на `kid` → пустой ключ) или SQL-инъекцию, если `kid` идёт в запрос к БД.
- **Слабый/угадываемый secret**: если `alg=HS256`, попробуй брутфорс секрета по словарю (`hashcat -m 16500` offline, без нагрузки на сервер) — частая находка: `secret`, `changeme`, название проекта.
- **Отсутствие проверки `aud`/`iss`**: токен, выпущенный для другого клиента/сервиса, принимается текущим API. Проверь, валидирует ли сервер `audience`/`issuer`, а не только подпись и `exp`.
- **`exp` в далёком будущем / отсутствует**: раскодируй payload, проверь срок жизни токена; чрезмерно долгоживущие access-токены — риск при утечке.

### OAuth2 / OIDC / SSO (проверять всегда, если есть внешняя авторизация — Google/GitHub/корпоративный IdP)

**Что искать в коде**
- Валидация `redirect_uri`/`callback URL`: точное совпадение со списком (whitelist) vs проверка через `startsWith`/подстроку/regex — последнее почти всегда обходится.
- Наличие и проверка `state` (защита от CSRF в OAuth-флоу) и `PKCE` (`code_verifier`/`code_challenge`) для публичных клиентов.
- Проверка подписи и `nonce` в `id_token` (OIDC) — не просто декодирование без верификации.
- Куда пишутся токены после обмена (`access_token`, `refresh_token`) — localStorage vs httpOnly cookie; попадают ли в URL (query string) и, соответственно, в логи/`Referer`/историю браузера.

**Как подтвердить**
1. Замени `redirect_uri` на домен, похожий на легитимный, но контролируемый тобой (`https://legit-app.com.evil.example`, `https://legit-app.com@evil.example`, добавление `/../evil`) — проверь, принимает ли authorization server.
2. Убери или заменил параметр `state` в запросе на авторизацию — проверь, требует ли callback-эндпоинт его совпадения.
3. Если используется `code` flow без PKCE для публичного клиента (SPA/мобильное приложение) — попробуй перехватить/повторно использовать `authorization code` (code reuse) от другого сеанса.
4. Проверь, не попадает ли `access_token`/`code` в `Referer`-заголовок при переходе со страницы callback на сторонний ресурс (картинки/скрипты с внешних доменов).
5. Для id_token: подмени payload без пересчёта подписи — должен быть отклонён; если используется `alg=none` в id_token — тот же тест, что и для обычного JWT.

## Соответствие OWASP API Security Top 10

Приложение — API (NestJS), поэтому наравне с обычным OWASP Top 10 полезно сверяться с [OWASP API Security Top 10](https://owasp.org/API-Security/), где часть категорий сформулирована точнее для API:

| API Top 10 | Соответствие / уточнение | Что проверить дополнительно |
|---|---|---|
| API1: Broken Object Level Authorization | = IDOR/BOLA (A01) | см. выше |
| API2: Broken Authentication | = A07 | + JWT/OAuth deep-dive выше |
| API3: Broken Object Property Level Authorization | Excessive Data Exposure + Mass Assignment | Проверь, не возвращает ли API поля, которые не нужны клиенту (`password`, `internalNotes`, чужие связи) — фильтрация должна быть на сервере (`select`), а не «фронт просто не показывает». Проверь Mass Assignment: отправь в теле запроса лишние поля (`role: "admin"`, `isVerified: true`, `balance: 999999`) при регистрации/обновлении профиля — применяются ли они без валидации через DTO с `whitelist: true`. |
| API4: Unrestricted Resource Consumption | = Rate limiting/DoS, но шире | Лимиты не только на auth-эндпоинты, но и на дорогие операции (экспорт, поиск, генерация отчётов, загрузка больших файлов), лимиты на размер массивов в теле запроса (pagination abuse — `?limit=999999`). |
| API5: Broken Function Level Authorization | = BFLA, часть A01 | Проверь доступ к admin-функциям через изменение метода/версии эндпоинта, не только через явный `/admin` путь. |
| API6: Unrestricted Access to Sensitive Business Flows | Бизнес-логика | Доступна ли критичная бизнес-операция (покупка, перевод, регистрация) без ограничений — автоматизация ботом, обход капчи/подтверждения. |
| API7: Server Side Request Forgery | = A10 | см. выше |
| API8: Security Misconfiguration | = A05 | см. выше |
| API9: Improper Inventory Management | Устаревшие/недокументированные версии API | Проверь наличие старых версий (`/api/v1/` рядом с `/api/v2/`), забытых debug/internal эндпоинтов, staging-окружений, доступных снаружи. |
| API10: Unsafe Consumption of APIs | Доверие к сторонним API | Если приложение вызывает внешние API и доверяет их ответам без валидации (внедрение через ответ третьей стороны) — отдельный вектор, особенно при webhook-приёме данных от внешних сервисов. |

## A03: Injection (SQL / NoSQL / Command)

**SQL (Prisma)**
- В коде ищи `$queryRaw`/`$executeRaw` с конкатенацией строк.
- Динамически: в параметр подставь `' OR '1'='1` и варианты с комментарием `--`; сравни ответы (разные наборы данных / ошибки 500 / раскрытие структуры). Признак инъекции — поведение меняется от полезной нагрузки, а не только от валидных данных.

**NoSQL**
- Если используется Mongo-подобный слой: отправь в JSON-тело `{"$ne": null}` / `{"$gt": ""}` вместо строки и проверь, что фильтр обходится.

**Command**
- Параметры, попадающие в `exec`/`spawn`: проверь инъекцию через `;`, `&&`, `$(...)`, обратные кавычки (см. `payloads.md`).

## A04: Insecure Design

- Логика сброса пароля без второго фактора, неограниченные попытки, раскрытие существования аккаунта (user enumeration).
- Подтверди: разница ответа на «существующий/несуществующий» email при login/register/recovery.

## A05: Security Misconfiguration

- `origin: '*'` в CORS, отсутствие `helmet`, `Content-Security-Policy`, `HSTS`, `X-Frame-Options`, раскрытие stack trace в 500, `NODE_ENV=production` без выключения verbose-ошибок.
- Подтверди: `curl -I` к API — смотри заголовки; отправь невалидный JSON — посмотри, не утекает ли stack trace/пути.

## A06: Vulnerable Components

- `npm audit` (`npm run security:deps`), устаревшие версии пакетов, `package-lock.json`.

## A07: Auth Failures

- Перебор логина без rate limit, слабая политика паролей, `JWT` без `exp`, хранение refresh-токена в localStorage.
- Подтверди: несколько неудачных логинов подряд — блокируется ли; наличие лимитов на `/auth/login`.

## A08: Software and Data Integrity Failures

- Небезопасная десериализация, отсутствие проверки целостности зависимостей (lockfile, integrity hash).

## A09: Logging & Monitoring Failures

- Логирование паролей/токенов/ПДн в консоль или файлы. Ищи `console.log` с чувствительными полями, `logger.log(password)`.

## A10: SSRF

- URL/адрес из ввода передаётся в `axios`/`fetch`/`http.request`.
- Подтверди: передай `http://127.0.0.1:PORT`, `http://169.254.169.254/latest/meta-data/`, `http://[::1]`, `http://localhost` и проверь, выполняется ли запрос к внутреннему ресурсу (по времени ответа/контенту). Используй свой коллбэк-эндпоинт (e.g. webhook.site или локальный listener), чтобы увидеть факт обращения.

## Дополнительно (не в Top 10, но обязательно)

### XSS (reflected / stored / DOM)
- **Код**: `bypassSecurityTrustHtml`, `innerHTML`, `document.write` без `DOMPurify`; отражение ввода в ответе без экранирования.
- **Reflected**: в параметр подставь `<script>alert(document.domain)</script>` (или простой `<img src=x onerror=...>`) и проверь, попал ли в HTML-ответ без кодирования.
- **Stored**: сохрани пейлоад через форму/профиль и открой страницу, где он рендерится — сработал ли.
- **DOM**: пейлоад попадает в JS-контекст (`location.hash`, `location.search`) и вставляется в DOM без санитизации.
- Полезная нагрузка берётся из `payloads.md`; фиксируй, экранируется ли ввод (`&lt;script&gt;`).

### CSRF
- Мутирующие запросы с cookie-аутентификацией без `SameSite` и без CSRF-токена.
- Подтверди: проверь `Set-Cookie` на `SameSite`; если токен передаётся только в cookie и нет CSRF-токена/кастомного заголовка — CSRF вероятен. Приведи PoC-форму (HTML, автосабмит) как доказательство.

### File Upload / Path Traversal
- Загрузка без проверки расширения/MIME; чтение файлов по пользовательскому пути.
- Подтверди: загрузи `.html`/`.svg`/`.js`; подставь `../../etc/passwd` или `..%2f..%2f` в путь.

### Rate Limiting / DoS
- Отсутствие лимитов на auth-эндпоинтах, большие payload.
- Подтверди: N запросов подряд без задержки/блокировки.

## Как оформлять результат
Каждую подтверждённую находку веди по шаблону отчёта (см. SKILL.md, Фаза 4) с PoC-запросом, ожидаемым/фактическим ответом и местом в коде (для gray-box).
