# Продвинутые и нишевые векторы (за пределами OWASP Top 10)

OWASP Top 10 — это категории риска, а не полный список векторов атак. Этот файл закрывает то, что регулярно встречается в реальных AppSec-аудитах, но не выделено отдельной категорией в Top 10. Для каждого вектора: что искать в коде (SAST), как подтвердить на запущенном приложении (DAST), пейлоады — в `payloads.md`.

Раздел разбит на две части:
- **«Всегда проверять»** — применимо к любому веб-приложению независимо от стека.
- **«Условные модули»** — проверяй только если этот компонент реально присутствует в проекте (см. Фазу 0 в `SKILL.md`). Не трать время на GraphQL-специфичные тесты, если в проекте нет GraphQL — это даст ложную нагрузку и не относится к делу.

## Всегда проверять

### Business Logic / Race Conditions (TOCTOU)

- **Код**: операции «check-then-act» без атомарности — проверка остатка/статуса и последующее изменение выполняются раздельно (без транзакции, без `SELECT ... FOR UPDATE`, без unique constraint на уровне БД).
- **Подтверждение**: отправь один и тот же мутирующий запрос параллельно (10–20 одновременных запросов через `asyncio.gather`/`Promise.all`, сниппет в `payloads.md`; на `prod` — только с согласования и на тестовых ресурсах) — например, повторное применение промокода, множественное списание одного бонуса, двойное подтверждение одного заказа. Сравни итоговое состояние ресурса с ожидаемым (должно быть ровно одно успешное применение).
- Проверь также обход многошагового процесса — прямой вызов эндпоинта финального шага (оплата подтверждена/заказ создан) без прохождения предыдущих шагов.

### HTTP Parameter Pollution (HPP) и CSV / Formula Injection

- **HPP**: передача дублирующихся query/form параметров (`?userId=A&userId=B`) или массива вместо строки — проверь, не расходятся ли значения между слоем проверки прав (берёт первый элемент) и бизнес-логикой (берёт последний элемент или массив).
- **CSV / Formula Injection**: если в приложении есть экспорт данных в CSV/XLSX, проверь, экранируются ли пользовательские поля, начинающиеся с `=`, `+`, `-`, `@`, `\t`, `\r` (например, `=1+1`).

### Prototype Pollution (применимо к JavaScript / TypeScript)

- **Код**: глубокое рекурсивное слияние объектов (`lodash.merge`, `_.defaultsDeep`, кастомный deep-merge) с пользовательским JSON без фильтрации ключей `__proto__`, `constructor`, `prototype`.
- **Подтверждение**: отправь `{"__proto__": {"polluted": "1"}}` в маршрут, выполняющий слияние объектов; проверь появление свойства `polluted` на несвязанном объекте.
- Особенно критично в местах, где загрязнённое свойство прототипа влияет на авторизацию или сериализацию (`isAdmin`, `role`).

### JWT / OAuth — алгоритмические атаки и потоки авторизации

См. `owasp-top10.md` → разделы «JWT — углублённые атаки» и «OAuth2 / OIDC / SSO» (A02/A07) — там полный список: `alg=none`, RS256→HS256 key confusion, `kid`-injection, слабый secret, отсутствие проверки `aud`/`iss`, невалидируемый `redirect_uri`, отсутствие `state`/PKCE, id_token без проверки подписи/`nonce`. Пейлоады и шаговая инструкция для `alg=none` — в `payloads.md`.

### Open Redirect

- **Код**: параметры `redirect`/`next`/`returnUrl`/`redirect_uri` используются в `res.redirect()`/`window.location` без проверки по whitelist доменов.
- **Подтверждение**: подставь `//evil.example`, `{протокол}://{домен}@evil.example` и варианты из `payloads.md` — проверь, куда фактически уходит редирект.
- Риск: используется как шаг в фишинге и для обхода `redirect_uri` в OAuth-флоу.

### Clickjacking (активный PoC, не только заголовок)

- **Код**: отсутствие директивы CSP `frame-ancestors` (и заголовка `X-Frame-Options` для обратной совместимости) на страницах с чувствительными действиями (смена email/пароля, удаление аккаунта, подтверждение платежа). В режиме ASVS L2 требуется именно `frame-ancestors`.
- **Подтверждение**: не ограничивайся проверкой заголовка — собери реальный HTML-PoC с прозрачным `<iframe>` (сниппет в `payloads.md`) и убедись, что целевая кнопка кликабельна через оверлей.

### Session Fixation

- **Код**: session ID не перегенерируется после успешного логина (`req.session.regenerate()` отсутствует), либо приложение принимает session ID, переданный клиентом до аутентификации (например, через query-параметр `sessionId=`).
- **Подтверждение**: зафиксируй session ID до логина (получи cookie как анонимный пользователь), залогинься, проверь — остался ли тот же ID активным и привязанным к аутентифицированной сессии. Если да — атакующий, подсунувший жертве заранее известный ID, получает доступ к её сессии после логина.

### Web Cache Poisoning / Cache Deception

- **Код**: использование заголовков `X-Forwarded-Host`, `X-Forwarded-Proto`, `Host` при формировании абсолютных URL (письма сброса пароля, ссылки в ответах) без валидации; наличие reverse-proxy/CDN с кэшированием по неполному ключу (без учёта заголовков, влияющих на ответ).
- **Подтверждение**: отправь запрос с подменённым `X-Forwarded-Host: evil.example` — проверь, попадает ли этот домен в тело ответа (например, в ссылку сброса пароля) или кэшируется ли ответ с учётом инъекции для последующих пользователей. Для cache deception — добавь к пути статического ресурса несуществующее расширение (`/profile/.css`) и проверь, не закэшировался ли приватный ответ как публичный.

### HTTP Request/Response Smuggling (кратко)

- Актуально при наличии reverse-proxy/балансировщика (nginx, ALB, envoy) перед сервером приложения с рассинхроном обработки `Content-Length`/`Transfer-Encoding`.
- **Подтверждение** — продвинутая техника, требует осторожности (может затронуть чужие запросы через общий канал); проводи только с явного разрешения и в изолированной среде, не в проде без согласования. Обычно вне рамок обычного gray-box аудита приложения — фиксируй как теоретический риск, если инфраструктура неизвестна.

## Условные модули (только если присутствуют в стеке)

### XXE (если приложение принимает или разбирает XML / SOAP / SVG / DOCX)

- **Код**: парсинг XML без явного отключения `DTD` и внешних сущностей (`resolve_entities`, `FEATURE_SECURE_PROCESSING`, `disallow-doctype-decl`).
- **Подтверждение**: отправь XML с объявлением внешней сущности вместо обычного тела запроса; для blind-варианта — запрос на свой локальный listener (`payloads.md`). Детали — `attack-surface.md` (раздел 3d).

### SSTI (если используется серверная шаблонизация страниц / писем / PDF / отчётов)

- **Код**: шаблонизаторы (Jinja2, Twig, Thymeleaf, FreeMarker, EJS, Handlebars, Nunjucks, Pug, ERB, Razor, Tera и др.), где пользовательский ввод конкатенируется в строку шаблона *до* компиляции, а не передаётся как контекст данных.
- **Подтверждение**: безопасное выражение `${7*7}` / `{{7*7}}` / `<%= 7*7 %>` в поле, попадающем в шаблон — если рендерится `49` (или `'7777777'` для `{{7*'7'}}` в Jinja2), движок вычисляет выражения из ввода (`payloads.md`). Детали — `attack-surface.md` (раздел 3d).

### GraphQL (если в проекте есть GraphQL-сервер или схема)

- Introspection/playground выключены в production.
- Авторизация на уровне каждого resolver/field resolver — не только на корневом маршруте или модуле.
- Ограничение глубины/сложности запроса (depth limit, query complexity) — защита от alias/batching DoS.
- Verbose-ошибки (stack trace в `extensions`) не утекают в production.
- Детали и пейлоады — `attack-surface.md` (раздел 3c) и `payloads.md`.

### WebSocket / Real-time шлюзы (если в проекте используется WebSocket / Socket.IO / SignalR и т. п.)

- Авторизация на handshake **и** отдельно на каждом обработчике события/сообщения.
- Проверка прав перед вступлением в комнату/broadcast-группу.
- Валидация входных данных сообщений так же строго, как HTTP DTO.
- Лимиты на частоту сообщений и количество соединений с одного клиента/IP.
- Детали — `attack-surface.md` (раздел 3b).

### Файловое хранилище / S3-совместимое (если используется presigned URL, публичные бакеты)

- TTL и scope presigned URL — не слишком долгий срок действия, привязка к конкретному объекту/операции.
- Отсутствие публичного ACL на бакетах с приватными данными; проверка через анонимный запрос к прямому URL объекта.
- `Content-Type`/`Content-Disposition` и `X-Content-Type-Options: nosniff` при отдаче загруженных пользователем файлов — предотвращение XSS через отдачу `.html`/`.svg` как `text/html` (должно быть `Content-Disposition: attachment` или принудительный безопасный MIME-тип).

### Входящие Webhooks и платёжные коллбэки (если приложение принимает события от внешних сервисов)

- **Код**: проверяется ли криптографическая подпись запроса (например, HMAC-SHA256 по сырому телу запроса через constant-time сравнение) до обработки события; проверяется ли `timestamp` и уникальный идентификатор события (`event_id` / `idempotency_key`) для защиты от повторной отправки (replay).
- **Подтверждение**: отправь запрос на webhook-эндпоинт без заголовка подписи, с изменённым телом при старой подписи и повторно отправь ранее перехваченный валидный запрос.

### Интеграции с LLM / AI-агентами (если в приложении есть функции на базе языковых моделей)

- **Prompt Injection и системный контекст**: разделены ли системные инструкции и пользовательский ввод; не хранятся ли секреты в системном промпте; не попадает ли недоверенный внешний контент (веб-страницы, письма, документы других пользователей) в контекст модели с возможностью переопределить инструкции (Indirect Prompt Injection).
- **Изоляция данных (RAG / память)**: фильтруются ли документы векторного поиска и история диалогов по правам текущего пользователя и `tenantId` на уровне сервера до передачи в модель.
- **Небезопасная обработка вывода модели**: экранируется/санитизируется ли ответ LLM перед рендерингом в HTML/Markdown (защита от XSS и скрытых изображений с утечкой данных через URL) и перед передачей в SQL/команды/HTTP-клиенты.
- **Вызов инструментов (Tool Calling / Excessive Agency)**: каждый инструмент, вызываемый моделью от имени пользователя (чтение данных, изменение записей, отправка запросов), обязан проверять права текущего пользователя на сервере, а чувствительные действия — требовать явного подтверждения.
- **Ограничение потребления (Unbounded Consumption / Denial of Wallet)**: наличие лимитов на длину входного промпта, `max_tokens` и частоту платных вызовов к провайдеру LLM.
- Детали — `attack-surface.md` (раздел 3f).

### Мультитенантность / Cross-Tenant изоляция (если приложение B2B / SaaS с разделением по организациям/тенантам)

- **Код**: проверяется ли принадлежность запрашиваемого объекта, фильтра поиска, выгрузки отчёта, ключа кэша и фоновой задачи к `tenantId` / `organizationId` из серверной сессии текущего пользователя, а не из тела/заголовка запроса.
- **Подтверждение**: создай две тестовые организации (Tenant A и Tenant B), возьми идентификатор ресурса или `tenantId` организации B и выполни чтение/изменение/экспорт от имени пользователя организации A.
- Детали — `attack-surface.md` (раздел 3h).

### SSR / Server Actions / BaaS (если используется Next.js, Nuxt, Remix, SvelteKit, Supabase, PostgREST)

- **Server Actions (`'use server'`)**: прямой POST-вызов функции без UI — проверяется ли сессия/авторизация и схема аргументов в самой функции, а не только в UI или `layout.tsx`.
- **Сериализация SSR / RSC payload (`__NEXT_DATA__`, RSC Flight)**: проверь исходный HTML-код страницы — не сериализуются ли в клиентские компоненты лишние поля из БД (`passwordHash`, `secret`, чужие поля).
- **Row Level Security (Supabase / PostgREST)**: проверь прямой запрос к таблицам REST/GraphQL с публичным `ANON_KEY` — включён ли RLS и не читаются/изменяются ли чужие строки.
- Детали — `attack-surface.md` (раздел 3i).

## Как оформлять результат

Находки по этому файлу оформляются по тому же шаблону отчёта, что и остальные (см. `SKILL.md`, Фаза 4): severity, файл/строки, PoC-запрос, уязвимый фрагмент, рекомендация. Для условных модулей явно укажи в отчёте, что модуль присутствует в проекте — это обосновывает включение проверки.
