# Продвинутые и нишевые векторы (за пределами OWASP Top 10)

OWASP Top 10 — это категории риска, а не полный список векторов атак. Этот файл закрывает то, что регулярно встречается в реальных AppSec-аудитах, но не выделено отдельной категорией в Top 10. Для каждого вектора: что искать в коде (SAST), как подтвердить на запущенном приложении (DAST), пейлоады — в `payloads.md`.

Раздел разбит на две части:
- **«Всегда проверять»** — применимо к любому веб-приложению независимо от стека.
- **«Условные модули»** — проверяй только если этот компонент реально присутствует в проекте (см. Фазу 0 в `SKILL.md`). Не трать время на GraphQL-специфичные тесты, если в проекте нет GraphQL — это даст ложную нагрузку и не относится к делу.

## Всегда проверять

### XXE (XML External Entity)

- **Код**: любой XML/SOAP/SVG-парсинг (`xml2js`, `libxmljs`, `fast-xml-parser`, встроенный `DOMParser`) без явного отключения `DTD`/внешних сущностей.
- **Подтверждение**: отправь XML с `<!ENTITY xxe SYSTEM "file:///etc/passwd">` вместо обычного тела запроса; для blind-варианта — SSRF-подобный callback на свой listener. Пейлоады — `payloads.md`.
- Условие применимости: только если приложение принимает/парсит XML, SOAP или загружаемые SVG-файлы.

### SSTI (Server-Side Template Injection)

- **Код**: шаблонизаторы (EJS, Handlebars, Nunjucks, Pug) для email/PDF/отчётов, где пользовательский ввод попадает в шаблон *до* компиляции (например, `template.replace('{{name}}', userInput)` затем `render`, или прямая конкатенация строки шаблона).
- **Подтверждение**: `${7*7}` / `{{7*7}}` / `<%= 7*7 %>` в поле, которое попадает в письмо/документ — если в результате `49`, движок исполняет выражения. Далее — payload для конкретного движка (`payloads.md`).

### Prototype Pollution

- **Код**: `lodash.merge`, `_.defaultsDeep`, рекурсивный `Object.assign`, кастомный deep-merge с пользовательским JSON без фильтрации `__proto__`/`constructor`/`prototype`.
- **Подтверждение**: отправь `{"__proto__": {"polluted": "1"}}` в место, где объект мержится с пользовательским вводом; проверь появление поля `polluted` на несвязанном объекте в другом месте приложения.
- Особенно критично в местах, где загрязнённое свойство прототипа влияет на авторизацию/сериализацию (например, `isAdmin`, `toJSON`).

### Business Logic / Race Conditions (TOCTOU)

- **Код**: операции «check-then-act» без атомарности — проверка остатка/статуса и последующее изменение выполняются раздельно (без транзакции, без `SELECT ... FOR UPDATE`, без unique constraint на уровне БД).
- **Подтверждение**: отправь один и тот же мутирующий запрос параллельно (10–20 одновременных запросов через `asyncio.gather`/`Promise.all`, сниппет в `payloads.md`) — например, повторное применение промокода, множественное списание одного бонуса, двойное подтверждение одного заказа. Сравни итоговое состояние ресурса с ожидаемым (должно быть ровно одно успешное применение).
- Проверь также обход многошагового процесса — прямой вызов эндпоинта финального шага (оплата подтверждена/заказ создан) без прохождения предыдущих шагов.

### JWT / OAuth — алгоритмические атаки и потоки авторизации

См. `owasp-top10.md` → разделы «JWT — углублённые атаки» и «OAuth2 / OIDC / SSO» (A02/A07) — там полный список: `alg=none`, RS256→HS256 key confusion, `kid`-injection, слабый secret, отсутствие проверки `aud`/`iss`, невалидируемый `redirect_uri`, отсутствие `state`/PKCE, id_token без проверки подписи/`nonce`. Пейлоады и шаговая инструкция для `alg=none` — в `payloads.md`.

### Open Redirect

- **Код**: параметры `redirect`/`next`/`returnUrl`/`redirect_uri` используются в `res.redirect()`/`window.location` без проверки по whitelist доменов.
- **Подтверждение**: подставь `//evil.example`, `https://legit.com@evil.example` и варианты из `payloads.md` — проверь, куда фактически уходит редирект.
- Риск: используется как шаг в фишинге и для обхода `redirect_uri` в OAuth-флоу.

### Clickjacking (активный PoC, не только заголовок)

- **Код**: отсутствие `X-Frame-Options` и/или CSP `frame-ancestors` на страницах с чувствительными действиями (смена email/пароля, удаление аккаунта, подтверждение платежа).
- **Подтверждение**: не ограничивайся проверкой заголовка — собери реальный HTML-PoC с прозрачным `<iframe>` (сниппет в `payloads.md`) и убедись, что целевая кнопка кликабельна через оверлей.

### Session Fixation

- **Код**: session ID не перегенерируется после успешного логина (`req.session.regenerate()` отсутствует), либо приложение принимает session ID, переданный клиентом до аутентификации (например, через query-параметр `sessionId=`).
- **Подтверждение**: зафиксируй session ID до логина (получи cookie как анонимный пользователь), залогинься, проверь — остался ли тот же ID активным и привязанным к аутентифицированной сессии. Если да — атакующий, подсунувший жертве заранее известный ID, получает доступ к её сессии после логина.

### Web Cache Poisoning / Cache Deception

- **Код**: использование заголовков `X-Forwarded-Host`, `X-Forwarded-Proto`, `Host` при формировании абсолютных URL (письма сброса пароля, ссылки в ответах) без валидации; наличие reverse-proxy/CDN с кэшированием по неполному ключу (без учёта заголовков, влияющих на ответ).
- **Подтверждение**: отправь запрос с подменённым `X-Forwarded-Host: evil.example` — проверь, попадает ли этот домен в тело ответа (например, в ссылку сброса пароля) или кэшируется ли ответ с учётом инъекции для последующих пользователей. Для cache deception — добавь к пути статического ресурса несуществующее расширение (`/profile/.css`) и проверь, не закэшировался ли приватный ответ как публичный.

### HTTP Request/Response Smuggling (кратко)

- Актуально при наличии reverse-proxy/балансировщика (nginx, ALB) перед Node-приложением с рассинхроном обработки `Content-Length`/`Transfer-Encoding`.
- **Подтверждение** — продвинутая техника, требует осторожности (может затронуть чужие запросы через общий канал); проводи только с явного разрешения и в изолированной среде, не в проде без согласования. Обычно вне рамок обычного gray-box аудита приложения — фиксируй как теоретический риск, если инфраструктура неизвестна.

## Условные модули (только если присутствуют в стеке)

### GraphQL (если используется `@nestjs/graphql`, Apollo/Mercurius)

- Introspection/playground выключены в production.
- Авторизация на уровне каждого resolver/field resolver — не только на модуле.
- Ограничение глубины/сложности запроса (`graphql-depth-limit`, `graphql-query-complexity`) — защита от alias/batching DoS.
- Verbose-ошибки (stack trace в `extensions`) не утекают в production.
- Детали и пейлоады — `nestjs-attack-surface.md` (раздел 1c) и `payloads.md`.

### WebSocket / Gateways (если используется `@nestjs/websockets`)

- Авторизация на handshake **и** отдельно на каждом `@SubscribeMessage`.
- Проверка прав перед вступлением в комнату/broadcast-группу.
- Валидация входных данных сообщений так же строго, как REST DTO.
- Лимиты на частоту сообщений и количество соединений с одного клиента/IP.
- Детали — `nestjs-attack-surface.md` (раздел 1b).

### Файловое хранилище / S3-совместимое (если используется presigned URL, публичные бакеты)

- TTL и scope presigned URL — не слишком долгий срок действия, привязка к конкретному объекту/операции.
- Отсутствие публичного ACL на бакетах с приватными данными; проверка через анонимный запрос к прямому URL объекта.
- `Content-Type`/`Content-Disposition` при отдаче загруженных пользователем файлов — предотвращение XSS через отдачу `.html`/`.svg` как `text/html` (должно быть `Content-Disposition: attachment` или принудительный безопасный MIME-тип).

## Как оформлять результат

Находки по этому файлу оформляются по тому же шаблону отчёта, что и остальные (см. `SKILL.md`, Фаза 4): severity, файл/строки, PoC-запрос, уязвимый фрагмент, рекомендация. Для условных модулей явно укажи в отчёте, что модуль присутствует в проекте — это обосновывает включение проверки.
