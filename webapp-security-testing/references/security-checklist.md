# Чек-лист проверки безопасности (SAST)

Статический чек-лист для инспекции кода. Проходи по нему при анализе каждого модуля/файла, а найденные кандидаты затем подтверждай динамически (см. `owasp-top10.md`). Различай «подтверждённую уязвимость» и «теоретический риск» — для последних явно указывай контекст и условия эксплуатации.

## А. Аутентификация и контроль доступа (AuthN / AuthZ / IDOR)

- Проверка авторизации на каждом эндпоинте (наличие Guard / Middleware).
- Уязвимости BOLA/IDOR: пользователь имеет право обращаться к ресурсу по `id` (например, `userId` берётся из доверенного токена сессии, а не слепо из `req.params`).
- Корректность JWT/сессий: алгоритм, срок действия, безопасное хранение refresh-токенов.

## Б. Валидация входных данных и инъекции (Input Validation & Injections)

- SQL / NoSQL / Command Injection: строго параметризованные запросы / ORM / Query Builder. Отсутствие конкатенации строк в запросах к БД.
- Валидация схемы: входящие DTO валидируются через строгие схемы (`zod`, `class-validator`, `joi`) до попадания в контроллеры и сервисы.
- Path Traversal: санитизация путей к файлам, запрет произвольного чтения через `../` или невалидированные имена файлов.
- SSRF: валидация исходящих URL по белым спискам, блокировка запросов к внутренним IP (`127.0.0.1`, `169.254.169.254`, `localhost`).

## В. Клиентская безопасность (XSS, CSRF, Headers)

- Отсутствие небезопасного рендеринга (`dangerouslySetInnerHTML`, `bypassSecurityTrustHtml` без санитизации через DOMPurify).
- Наличие CSRF-защиты для мутирующих запросов с cookie-аутентификацией (`SameSite=Strict/Lax`, CSRF-токены).
- Безопасные заголовки (Helmet, Content-Security-Policy, HSTS, X-Frame-Options).

## Г. Утечки данных и секреты (Sensitive Data Exposure)

- Отсутствие API-ключей, паролей, приватных сертификатов в репозитории.
- Отсутствие логирования чувствительных данных (паролей, номеров карт, ПДн, токенов) в консоль или лог-файлы.
- Конфигурация `.gitignore` и шаблонов `.env.example`.

## Д. Отказоустойчивость и DoS (Rate Limiting & Resource Exhaustion)

- Наличие Rate Limiting на публичных эндпоинтах (особенно `/auth/login`, `/register`, `/recovery`).
- Ограничение размера загружаемых файлов и payload запросов (`body-parser limits`).
- Защита от ReDoS (катастрофического возврата в регулярных выражениях).

## Е. Бизнес-логика и race conditions (TOCTOU)

- Повторное использование одноразового ресурса: промокод/купон, приглашение, ссылка на сброс пароля, идемпотентность платежа — есть ли блокировка на уровне БД (транзакция, unique constraint, `SELECT ... FOR UPDATE`) или проверка «check-then-act» уязвима к гонке.
- Списание/пополнение баланса, лимитов, квот — не выполняются ли проверка остатка и списание раздельными неатомарными операциями.
- Многошаговый workflow (оформление заказа, KYC, подтверждение email/телефона) — можно ли обратиться напрямую к эндпоинту финального шага, минуя промежуточные проверки.
- Автоматизация массовых действий ботом там, где предполагается «один пользователь — одно действие» (голосование, лайки, реферальные бонусы).

## Ж. OAuth / OIDC / SSO

- Валидация `redirect_uri`/`callbackURL` строго по whitelist (точное совпадение), а не по префиксу/подстроке/regex.
- Наличие и проверка `state` (защита от CSRF в OAuth-потоке) и `PKCE` (`code_verifier`/`code_challenge`) для публичных клиентов.
- Проверка подписи и `nonce` в `id_token` (OIDC), а не только декодирование без верификации.
- Связывание внешнего аккаунта с локальным по email без подтверждения владения (`email_verified`) — риск account takeover.
- Хранение и место передачи `access_token`/`refresh_token`/`code` — не попадают ли в URL, `Referer`, логи.

## З. Продвинутые инъекции (проверять при наличии соответствующей функциональности)

- **XXE** — если есть парсинг XML/SOAP/SVG: включён ли `DTD`/external entities в XML-парсере (`libxmljs`, `xml2js` с `explicitArray`/`resolve`, встроенный `DOMParser`).
- **SSTI** — если есть шаблонизация email/PDF/документов (EJS, Handlebars, Nunjucks, Pug): пользовательский ввод не должен попадать в строку шаблона до компиляции, только как данные для подстановки.
- **Prototype Pollution** — глубокое объединение объектов (`lodash.merge`, `_.defaultsDeep`, рекурсивный `Object.assign`) с пользовательским JSON без фильтрации `__proto__`/`constructor`/`prototype`.

## И. Open Redirect / Clickjacking / Cache Poisoning

- Redirect-параметры (`redirect`, `next`, `returnUrl`, `redirect_uri`) валидируются по whitelist доменов/путей, а не проверкой `startsWith('/')` (обходится `//evil.example`) или наличием домена в строке.
- Заголовок `X-Frame-Options` или CSP `frame-ancestors` присутствует на страницах с чувствительными действиями (не только теоретически — подтверждается активным PoC с `<iframe>`).
- Обработка заголовков `X-Forwarded-Host`/`X-Forwarded-Proto`/`Host` — не используются ли они без валидации при формировании абсолютных URL (риск web cache poisoning / password reset poisoning).

## К. Опциональные модули (проверять только если присутствуют в стеке)

- **GraphQL**: `introspection`/`playground` отключены в production; авторизация на уровне каждого resolver/field resolver, а не только на модуле; ограничение глубины и сложности запроса (защита от alias/batching DoS).
- **WebSocket / Gateways**: авторизация на этапе handshake **и** на уровне каждого `@SubscribeMessage`; проверка прав перед вступлением в комнату/канал (`socket.join`); лимиты на частоту сообщений от одного клиента.
- **Файловое хранилище (S3-совместимое)**: TTL и scope presigned URL, отсутствие публичного ACL на приватных бакетах, проверка `Content-Type` при отдаче файлов (защита от XSS через отдачу пользовательского HTML/SVG как `text/html`).

## Правила работы с чек-листом

- Не проводи рефакторинг стиля кода или оптимизацию скорости, если они не влияют на безопасность. Не трогай работающую бизнес-логику.
- Не предлагай решения, ослабляющие защиту: wildcard в CORS (`origin: '*'`), отключение валидации SSL/TLS (`rejectUnauthorized: false`), отключение CSP, захардкоженные токены/пароли.
- Любой входной параметр, файл, заголовок или внешний API-ответ по умолчанию считай скомпрометированным (zero trust).
- Если риск теоретический (edge case) — явно укажи контекст и условия эксплуатации, избегай ложноположительных срабатываний (False Positives).
