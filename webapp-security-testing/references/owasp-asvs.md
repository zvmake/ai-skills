# Режим ASVS — проверка соответствия OWASP ASVS

OWASP Application Security Verification Standard (ASVS) — это стандарт проверки мер защиты веб-приложений и API. В отличие от OWASP Top 10 (списка частых категорий риска), ASVS — это перечень проверяемых требований к архитектуре, коду и конфигурации. По каждому требованию выносится статус выполнения с доказательством.

Режим отвечает на вопрос «соответствует ли приложение целевому уровню ASVS». Режим Pentest отвечает на вопрос «какие уязвимости в приложении можно проэксплуатировать».

## 1. Когда режим включается

- **Только по явному запросу**, в котором назван `ASVS`: «аудит по ASVS L2», «ASVS L1, главы V6–V8», «проверка соответствия OWASP ASVS».
- Запросы «OWASP», «OWASP Top 10», «проверь безопасность», «пентест» без слова `ASVS` режим ASVS **не включают**: по ним сразу выполняется режим Pentest (`SKILL.md`).
- Если пользователь просит «проверить на соответствие стандарту безопасности», но не назвал стандарт — уточни, нужен ли режим Pentest или аудит по OWASP ASVS.

## 2. Выбор уровня

Уровни накопительные: L2 включает все требования L1, L3 включает все требования L1 и L2. Точное число требований для каждого уровня выводит скрипт `scripts/asvs_requirements.py` по загруженному релизу стандарта (ориентировочно: L1 — ~70, L2 — ~250, L3 — ~345). Требования к документации и архитектурным решениям встречаются на всех трёх уровнях (включая L1 и L2), а на L3 их доля максимальна.

Если уровень в запросе не указан, **задай вопрос и дождись ответа**. Не выбирай уровень сам, в том числе по чувствительности данных. Текст вопроса:

> Укажите уровень OWASP ASVS:
> - **L1** — базовая защита: приложения с низким риском, первый шаг к соответствию;
> - **L2** (рекомендуется) — большинство приложений с персональными и бизнес-данными;
> - **L3** — критичные системы: финансы, медицина, госсектор, высокая ценность данных.
>
> Часть требований (документация, внешняя инфраструктура, организационные меры) при отсутствии данных в репозитории потребует подтверждения владельцем системы. Можно ограничить проверку главами, например «L2, V6–V8».

## 3. Источник требований

Приоритет источников:

1. **Последний стабильный релиз** из https://github.com/OWASP/ASVS/tags (через список релизов репозитория). Берутся только стабильные релизы с тегами вида `vX.Y.Z` / `vX.Y.Z_release` (черновые `draft`, `prerelease` и постоянно меняющийся тег `latest` игнорируются). Если у самого нового тега ещё нет прикреплённого CSV-файла `*_en.csv`, скрипт автоматически проверяет предыдущий стабильный релиз.
2. **Приложенный CSV** `references/owasp-asvs.csv` (или пользовательский файл через `--csv`), если скачать или разобрать релиз из сети не удалось (нет интернета, лимит GitHub API, сменился формат).

Оба шага выполняет кроссплатформенный скрипт `scripts/asvs_requirements.py` (работает на Linux, macOS и Windows, требует только стандартную библиотеку Python 3.8+):

```bash
python scripts/asvs_requirements.py --level 2 --out ./asvs-checklist-L2.md
python scripts/asvs_requirements.py --level 2 --chapters V6-V8 --out ./asvs-checklist-L2.md
python scripts/asvs_requirements.py --level 2 --offline --out ./asvs-checklist-L2.md
python scripts/asvs_requirements.py --level 2 --csv /path/to/custom-asvs.csv --out ./asvs-checklist-L2.md

# Пакетное обновление статусов в чек-листе без ручного редактирования большого файла:
python scripts/asvs_requirements.py --update ./asvs-checklist-L2.md \
    --set "V6.2.1|SAST + DAST|Pass|src/auth/dto.ts:18 — minLength(12)" \
    --set "V6.2.4|SAST|Fail|См. карточку [MEDIUM] Отсутствует проверка по списку утечек"
```

Особенности работы скрипта:
- Аргумент `--chapters` принимает список или диапазон глав (`V6,V7,V8`, `V6-V8`, `V6–V8`, `6-8`).
- Если выходной файл `--out` уже существует, скрипт **не перезаписывает** его без флага `--force`, чтобы не потерять уже заполненный прогресс проверки.
- Флаг `--update <файл>` с одним или несколькими `--set "REQ_ID|МЕТОД|СТАТУС|ДОКАЗАТЕЛЬСТВО"` точечно обновляет строки таблицы без переписывания всего файла в контексте модели.
- Скрипт выводит источник (скачанный релиз с версией и URL либо локальный CSV с причиной) и распределение требований по уровням — перенеси эти данные в раздел `0. Параметры проверки` отчёта. При лимите GitHub API можно задать переменную окружения `GITHUB_TOKEN`.

Если Python в среде недоступен, выполни те же шаги вручную: скачай CSV последнего стабильного релиза (`*_en.csv` без `legacy` в имени) или возьми `references/owasp-asvs.csv` и отфильтруй строки с `L <= выбранный_уровень`. Колонки CSV: `chapter_id, chapter_name, section_id, section_name, req_id, req_description, L`.

**Не формулируй требования по памяти.** Текст и идентификаторы (`req_id`, например `V6.2.1`) берутся строго из CSV.

## 4. Рабочий цикл

1. **Скоуп.** Зафиксируй уровень, главы, окружение (prod / stage / локально) и доступы: код, конфигурация окружений, логи, документация, настройки IdP. Правила раздела «Границы и правила» из `SKILL.md` действуют полностью.
2. **Recon (Фазы 0–1 из `SKILL.md`).** Определи стек, построй карту маршрутов и зафиксируй присутствующие в проекте условные модули — это необходимо для корректной оценки применимости (`N/A`).
3. **Рабочий чек-лист.** Сформируй чек-лист скриптом `scripts/asvs_requirements.py`. Сохраняй файл в постоянный каталог отчётов/артефактов сессии (вне отслеживаемых исходников приложения или в путь, указанный пользователем), чтобы ссылка на него в итоговом отчёте оставалась доступной.
4. **Применимость (`N/A`).** Сразу отметь `N/A` для разделов, функциональности которых в приложении объективно нет (например: WebRTC, GraphQL, WebSocket, MFA, OAuth Authorization Server, неуправляемый код), с кратким доказательством отсутствия по результатам Recon.
5. **Проверка по главам (батчами без потери качества).** Проверяй главы последовательно по убыванию риска (для стандартной структуры глав ASVS: V8 → V6 → V7 → V9 → V10 → V1 → V2 → V5 → V3 → V4 → V13 → V12 → V14 → V11 → V15 → V16 → V17; если в новой версии стандарта нумерация глав изменилась — ориентируйся на названия глав). При полном прогоне L2/L3 двигайся пачками по 3–4 главы, проверяя **каждое подусловие** внутри текста требования перед выставлением `Pass`. Способ проверки — по таблице в разделе 6.
6. **Фиксация прогресса.** В сгенерированном чек-листе у всех пунктов стоит начальный статус `—` (ещё не проверено). После проверки каждой главы (или пачки глав) записывай результаты через `python scripts/asvs_requirements.py --update <файл> --set ...`, заменяя `—` на `Pass` / `Fail` / `N/A` / `Not verified`. При продолжении работы после паузы или переполнения контекста проверь оставшиеся строки со статусом `—` (`grep "| — |"`) и продолжай с первой такой строки.
7. **Отчёт.** Сформируй итоговый отчёт по шаблону из раздела 7.

Все уязвимости, обнаруженные попутно и выходящие за рамки проверяемых требований ASVS, включаются в раздел 5 отчёта как дополнительные находки.

## 5. Статусы и методы

**Методы проверки:**
- `SAST` — анализ исходного кода;
- `DAST` — динамическая проверка на запущенном приложении (запрос и ответ);
- `CFG` — конфигурация окружения, инфраструктуры, веб-сервера, сборки и зависимостей (SCA);
- `DOC` — документация проекта или подтверждение владельцем системы.

Для требований, предполагающих динамическую проверку (`DAST`), действует правило 6 из `SKILL.md`. Требования, которые по своей природе проверяются методами `SAST`, `CFG` или `DOC`, динамического HTTP-запроса не требуют (пункт `д` правила 6 в `SKILL.md`).

**Статусы в чек-листе:**

| Статус | Когда ставится | Что обязательно указать в колонке доказательства |
|---|---|---|
| `—` | Начальный маркер при генерации чек-листа (требование ещё не проверено) | К моменту завершения аудита строк со статусом `—` в выбранном скоупе остаться не должно. |
| `Pass` | Есть фактическое доказательство выполнения требования | Точный `файл:строка`, HTTP-запрос/ответ, параметр конфигурации или ссылка на документ. Формулировка «проблем не найдено» без указания проверенного места не допускается. |
| `Fail` | Есть доказательство невыполнения требования | Краткая суть дефекта и ссылка на карточку несоответствия в разделе 2 отчёта. |
| `N/A` | Функциональности, к которой относится требование, в системе нет | Доказательство отсутствия (нет соответствующих зависимостей, маршрутов, схем, модулей). |
| `Not verified` | Требование применимо, но проверить его в рамках текущих доступов невозможно | Точная причина и что требуется для проверки: доступ к prod-конфигурации/логам/IdP, подтверждение владельцем системы, либо пропуск DAST по причинам (а/б/в) из правила 6 `SKILL.md`. |

**Требования к документации** (разделы со словом `Documentation` в `section_name` и требования, содержащие `documented` / `documentation` в `req_description`). Сначала ищи документацию в репозитории (`docs/`, `README*`, ADR, OpenAPI/Swagger, комментарии к схемам). Если документации в репозитории нет — ставь `Not verified` и выноси вопрос владельцу системы в раздел 3 отчёта. Статус `Fail` ставится только если владелец подтвердил отсутствие документации либо найденный документ противоречит требованию или фактической реализации.

**Severity** для карточек `Fail` определяется реальным риском эксплуатации (по шкале из Фазы 4 `SKILL.md`), а не номером уровня L1/L2/L3.

## 7. Шаблон отчёта (режим ASVS)

```markdown
### 0. Параметры проверки
| Параметр | Значение |
|---|---|
| Стандарт | OWASP ASVS (<версия/источник из вывода скрипта>) |
| Уровень | L<N> |
| Главы | все / перечень |
| Целевой стенд и окружение | {протокол}://{домен}:{порт} (local / test / stage / prod) |
| SAST | done / skipped (причина) |
| DAST | done / skipped (причина) |
| Рабочий чек-лист | <путь к файлу> |

### 1. Сводка соответствия
| Глава | Требований | Pass | Fail | N/A | Not verified |
|---|---|---|---|---|---|
| V1 ... | | | | | |
| Итого | | | | | |

Вывод: <соответствует / не соответствует / соответствие не подтверждено> уровню L<N>.

### 2. Несоответствия (Fail)
#### [SEVERITY] Название (<req_id> / CWE-XXX)
- Требование ASVS: <req_id> — краткая суть
- Метод подтверждения: DAST / SAST / CFG / DOC
- Файл и строки / конфигурация / документ
- Описание несоответствия
- Доказательство (PoC-запрос и ответ — для DAST; точный фрагмент кода/конфигурации — для SAST/CFG)
- Рекомендация

### 3. Не проверено и вопросы владельцу (Not verified)
| Требование | Причина / что нужно для проверки |
|---|---|

### 4. Неприменимо (N/A)
| Глава / раздел | Обоснование отсутствия функциональности |
|---|---|

### 5. Дополнительные находки вне ASVS
(в формате карточек из SKILL.md)
```

Правила вывода в разделе 1:
- «**Соответствует** уровню L<N>» — только если в выбранном скоупе нет ни одного `Fail` и ни одного `Not verified` (все применимые пункты имеют статус `Pass`). Если проверялись не все главы, явно укажи: «Соответствует уровню L<N> в рамках проверенных глав (<перечень>)».
- «**Не соответствует** уровню L<N>» — если есть хотя бы один `Fail`.
- «**Соответствие не подтверждено**» — если `Fail` нет, но остаётся хотя бы один пункт `Not verified`.

Полный рабочий чек-лист в текст отчёта не копируется: в разделе 0 указывается путь к сохранённому файлу чек-листа.
