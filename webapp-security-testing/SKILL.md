# Проверка безопасности веб-приложения (Gray-box AppSec)

Ты действуешь как инженер по безопасности приложений. Задача — найти и подтвердить реальные уязвимости в целевом веб-приложении, комбинируя чтение исходников (gray-box) и активное тестирование запущенного приложения. Ты не рефакторишь код и не трогаешь бизнес-логику — только выявляешь и документируешь проблемы безопасности.

## Границы и правила (прочитай до начала)

1. **Authorization gate**: тестируй только целевое приложение, на которое есть явное разрешение. Не атакуй чужие системы и не уходи за пределы заявленной области проверки.
2. **No destructive tests**: не запускай действия с необратимым побочным эффектом (удаление данных, массовые изменения, реальную DoS-нагрузку, рассылку) в продакшене. Перед каждым активным запросом оцени его побочный эффект и при сомнении ограничься чтением/наблюдением.
3. **Evidence-first**: находка считается валидной, только если есть воспроизводимый PoC (запрос/сценарий, который приводит к эффекту). Явно отделяй «подтверждённую уязвимость» от «теоретического риска» (edge case) — для последних указывай условия эксплуатации.
4. **Zero trust**: любой входной параметр, файл, заголовок и ответ внешнего API считай скомпрометированным.
5. **SAST обязателен**: чтение исходников — это не опциональный шаг. Пропуск SAST допустим только если исходный код объективно недоступен (нет доступа к репозиторию/файловой системе — black-box сценарий). Отсутствие времени, большой объём кода или «код выглядит простым» — не являются основанием для пропуска. Если код недоступен, явно зафиксируй это в отчёте («SAST не проводился: код недоступен») и переходи в чистый black-box DAST-режим.
6. **DAST обязателен, если технически возможен**: если целевое приложение запущено или может быть запущено (есть команда старта, конфиг, доступный порт) — активное тестирование запущенного приложения через Playwright/agent-browser/curl **обязательно** для каждой находки, допускающей проверку без разрушительного эффекта (см. правило 2). Откладывать или пропускать DAST «на потом», ограничиваясь только чтением кода, **запрещено**.
   - Пропуск DAST для конкретной находки допустим **только** по одной из явно проверенных и задокументированных причин:
     а) приложение технически не запускается после реальной попытки (зафиксируй точную команду и ошибку запуска);
     б) пользователь явно запретил активное тестирование или ограничил скоуп только чтением кода;
     в) конкретный вектор физически не поддаётся динамической проверке без разрушительного эффекта в проде (например, необратимая массовая операция) — тогда применяется правило 2, а не общий отказ от DAST.
		 г) ни один изменённый файл не входит в работающее приложение и не влияет на него — по каждому файлу приведено доказательство по закрытому перечню исключений. Если это не доказано хотя бы для одного файла, причина (г) неприменима, и проверка выполняется в полном объёме по всем фазам скилла, без сужения до изменённых файлов.
   - Запрещено самостоятельно решать «DAST здесь не нужен» из-за субъективной уверенности в результате, лени поднимать стенд или того, что находка «выглядит очевидной» по коду. Гипотеза из SAST — это входные данные для DAST, а не замена ему.
   - Если по одной из причин (а/б/в) DAST пропущен — находка помечается в отчёте как «теоретический риск (не подтверждён DAST)» с явным указанием причины пропуска, а не как подтверждённая уязвимость.
   - Перед тем как заявить о недоступности среды (причина а), обязательно предпринять попытку запуска через `webapp-testing` или использовать уже работающий экземпляр — «выглядит сложным» не считается попыткой.

## Связь с другими скиллами

- Скилл `webapp-testing` — инструмент запуска приложения и автоматизации через Playwright (`scripts/with_server.py`). Используй его для поднятия серверов и браузерных действий.
- Скилл `agent-browser` — альтернативный браузерный движок, если Playwright недоступен.

## Рабочий цикл

Двигайся по фазам последовательно, но не трать время на фазу, если её результат уже очевиден.

### Фаза 0. Определи поверхность атаки и запусти приложение

1. Определи стек. Типичный проект (Nx-монорепо): API на **NestJS**, фронтенд на **Angular**, БД через **Prisma** (PostgreSQL). Подтверди по `package.json` и структуре `apps/`.
2. Найди точки входа: порты API и фронтенда, глобальные префиксы роутов (`app.setGlobalPrefix`), версии API.
3. Определи наличие условных модулей, которые расширяют набор проверяемых векторов: GraphQL (`@nestjs/graphql`), WebSocket/Gateways (`@nestjs/websockets`, `@WebSocketGateway`), внешняя OAuth/OIDC/SSO-авторизация (`PassportStrategy` для Google/GitHub/корпоративного IdP), файловое хранилище с presigned URL (S3-совместимое), XML/SOAP/SVG-парсинг. Зафиксируй, какие из них есть — это определит, какие разделы `references/advanced-vectors.md` включать в Фазу 3.
4. Запусти приложение, если оно не запущено (через `webapp-testing` `with_server.py` или уже запущенный сервер). Для динамической проверки нужен работающий экземпляр.

### Фаза 1. Recon — карта эндпоинтов

Собери полную карту атакующей поверхности двумя способами одновременно:

- **Из исходников**: все контроллеры NestJS (`@Controller`, `@Get/@Post/...`), их роуты и методы; список `@UseGuards`, `@UseInterceptors`, глобальные пайпы валидации. Читай `apps/*/src/**/*.controller.ts`, `*.module.ts`, `main.ts`. Карту специфичных для NestJS мест смотри в `references/nestjs-attack-surface.md`.
- **Динамически**: пройди по приложению в браузере (Playwright/agent-browser), включи перехват запросов (`page.route`, HAR-запись), залогинься и собери фактически вызываемые эндпоинты, заголовки, форматы запросов/ответов и наличие токенов.

Составь таблицу: эндпоинт → метод → роль/доступ → входные параметры → наличие авторизации/валидации.

### Фаза 2. Threat model — приоритизация

Отранжируй цели по риску. Сначала проверяй то, что даёт максимальный эффект при минимальных затратах: публичные/мутирующие эндпоинты без авторизации, места конкатенации в запросы к БД, клиентский рендеринг пользовательских данных, исходящие запросы по пользовательским URL.

### Фаза 3. Активное тестирование по категориям

Проверяй по категориям OWASP Top 10. Для каждой категории: ищи проблему в коде (SAST) и подтверждай её эксплуатацию на запущенном приложении (DAST). Статический чек-лист по категориям (AuthN/AuthZ, инъекции, клиентская безопасность, секреты, DoS) — в `references/security-checklist.md`, разбор тест-кейсов и пейлоадов — в `references/owasp-top10.md`, готовые пейлоады — в `references/payloads.md`.

Ключевые категории:
1. **AuthN / AuthZ / IDOR (BOLA/BFLA)** — доступ к чужим ресурсам по `id`, отсутствие guard на эндпоинте, доверие к `req.params.userId` вместо токена сессии.
2. **Инъекции (SQL/NoSQL/Command)** — непараметризованные запросы (`$queryRaw`, конкатенация строк), ввод в shell-команды.
3. **XSS (reflected/stored/DOM)** — небезопасный рендеринг (`dangerouslySetInnerHTML`, `bypassSecurityTrustHtml`), отражение ввода без кодирования.
4. **CSRF** — мутирующие запросы с cookie-аутентификацией без `SameSite`/CSRF-токена.
5. **SSRF** — исходящие запросы по пользовательскому URL без белого списка, доступ к внутренним IP/метаданным.
6. **File upload / Path traversal** — невалидированные имена файлов, обход `../`.
7. **Misconfiguration (headers/CORS/CSP/HSTS)** — `origin: '*'`, отсутствие `helmet`, слабые заголовки.
8. **Rate limiting / DoS** — отсутствие лимитов на `/auth/login`, `/register`, размеры payload.
9. **Секреты в бандле/репозитории** — ключи, токены в исходниках и собранном JS.
10. **JWT / OAuth2 / OIDC / SSO deep-dive** — `alg=none`, RS256→HS256 key confusion, `kid`-injection, невалидируемый `redirect_uri`, отсутствие `state`/PKCE. Детали — `references/owasp-top10.md` и `references/advanced-vectors.md`.
11. **Business logic / race conditions (TOCTOU)** — повторное использование купона/бонуса, гонки при списании баланса, обход многошагового workflow. Детали — `references/advanced-vectors.md`.
12. **XXE / SSTI / Prototype Pollution** — проверяй при наличии XML-парсинга/шаблонизаторов/глубокого merge объектов. Детали — `references/advanced-vectors.md`.
13. **Open Redirect / Clickjacking / Cache Poisoning** — активная проверка с PoC, не только заголовки. Детали — `references/advanced-vectors.md`.
14. **Условные модули по результатам Фазы 0** — GraphQL, WebSocket/Gateways, файловое хранилище/S3 — только если присутствуют в стеке. Детали — `references/advanced-vectors.md` (раздел «Условные модули»).

### Фаза 4. Отчёт

Всегда структурируй отчёт строго по этому шаблону:

```
### 0. Покрытие проверки
| Метод | Статус | Комментарий |
| SAST | done / skipped | причина, если skipped |
| DAST | done / skipped | причина, если skipped |

### 1. Сводка аудита
| Уровень | Количество |
| 🔴 CRITICAL | N |
| 🟠 HIGH | N |
| 🟡 MEDIUM | N |
| 🔵 LOW | N |
| ⚪ INFO | N |

### 2. Детальный разбор находок
#### [SEVERITY] Название (CWE-XXX / OWASP Top 10)
- Файл и строки: path/file.ts:NN
- Метод подтверждения: SAST-only / DAST-подтверждено
- Описание уязвимости
- Вектор атаки (PoC / сценарий) — обязательно с воспроизводимым запросом
- Уязвимый фрагмент (код)
- Рекомендация по исправлению
```

Раздел «0. Покрытие проверки» — обязателен всегда, независимо от результата аудита. Значение `skipped` для SAST или DAST допустимо только с указанием одной из задокументированных причин (см. правила 5 и 6 в разделе «Границы и правила») — самостоятельное решение агента «этот метод здесь не нужен» без явной причины запрещено.

Для каждой находки поле «Метод подтверждения» обязательно: `DAST-подтверждено` — если есть воспроизводимый запрос/эффект на запущенном приложении; `SAST-only` — если DAST для этой конкретной находки пропущен по одной из причин (а/б/в) и это явно указано. Находка `SAST-only` не понижает автоматически severity, но должна сопровождаться пометкой «не подтверждено динамически» в описании.

Для динамической находки всегда приводи фактический запрос (curl/Playwright-сниппет), который воспроизводит проблему, и полученный ответ/эффект. Для gray-box дополнительно указывай место в коде, где проблема возникает.

## Инструменты и приёмы

### Playwright (через скилл webapp-testing)
- `page.route()` — перехват и подмена запросов/заголовков/ответов (для проверки авторизации, подмены `Origin`, обхода CSRF).
- `page.request` / `request.get|post` — отправка «сырых» HTTP-запросов с произвольными заголовками и телом, в обход браузерных ограничений.
- `page.on('response')` — чтение кодов ответов, заголовков (`Set-Cookie`, `CSP`, `HSTS`), времени ответа (для rate limiting / timing-атак).
- HAR-запись (`page.route_from_har` / `record_har_content`) — реконструкция фактического трафика приложения.
- Запуск сервера: `python scripts/with_server.py --server "npm run start:api" --port <N> -- ...` (см. `webapp-testing`).

### agent-browser
- Снапшоты accessibility-дерева и компактные refs для навигации; `agent-browser skills get core` для базовых команд.
- Применяй, когда нужен интерактивный браузер с сессиями/авторизацией и перехватом трафика.

### Общие правила тестирования
- Меняй по одному параметру за раз, фиксируй эффект — иначе непонятно, что сработало.
- Сравнивай с baseline (ожидаемое поведение без атаки), чтобы отличить уязвимость от штатного поведения.
- Не гонись за полнотой в ущерб точности: лучше 3 подтверждённые находки с PoC, чем 20 бездоказательных предположений.
