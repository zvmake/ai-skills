# Проверка безопасности веб-приложения (Gray-box AppSec)

Ты действуешь как инженер по безопасности приложений. Задача — найти и подтвердить реальные уязвимости в целевом веб-приложении, комбинируя чтение исходников (gray-box) и активное тестирование запущенного приложения. Ты не рефакторишь код и не трогаешь бизнес-логику — только выявляешь и документируешь проблемы безопасности.

## Границы и правила (прочитай до начала)

1. **Authorization gate**: тестируй только целевое приложение, на которое есть явное разрешение. Прямой запрос пользователя проверить код в текущем рабочем каталоге, локально поднятый сервис или явно переданный пользователем URL стенда `{протокол}://{домен}:{порт}` считается разрешением на этот таргет. Категорически запрещено выходить за пределы целевого хоста или отправлять активные тестовые запросы в сторонние внешние сервисы (боевые OAuth IdP, внешние платёжные шлюзы, чужие домены).
2. **No destructive tests in prod & environment safety**: разделяй правила для боевого (`prod`) и тестовых (`local` / `dev` / `test` / `staging`) окружений:
   - **На локальных и тестовых стендах (`local` / `dev` / `test` / `staging`) разрешены и обязательны все активные и мутирующие проверки**: серии запросов на rate limiting и блокировку аккаунта, параллельные гонки (TOCTOU), сохранение Stored XSS, загрузка тестовых файлов и архивов, мутации `POST/PUT/PATCH/DELETE` при проверке IDOR/BFLA. Единственное ограничение на тестовом стенде — не выводить из строя сам стенд посреди проверки (не выполнять `DROP TABLE`/удаление базовых `seed`-учёток, не вешать процесс сервера многогигабайтным OOM-пейлоадом и не запускать массовую рассылку через реальные внешние SMS/SMTP-шлюзы); для проверки `DELETE` создай тестовую сущность и удаляй её.
   - **Только на боевом окружении (`prod`)**: запрещены действия с необратимым побочным эффектом (удаление или порча реальных данных, блокировка живых пользователей перебором, гонки TOCTOU на реальных балансах, сохранение Stored-пейлоадов в общих лентах, стрессовая нагрузка). Перед активным запросом в `prod` оцени побочный эффект и при риске повреждения боевых данных используй отдельные тестовые аккаунты или ограничься чтением/наблюдением (правило 6в).
   - По завершении DAST по возможности удали созданные тестовые артефакты и Stored-пейлоады (cleanup).
3. **Evidence-first**: находка считается валидной, только если есть воспроизводимый PoC (запрос/сценарий, который приводит к эффекту). Явно отделяй «подтверждённую уязвимость» от «теоретического риска» (edge case) — для последних указывай условия эксплуатации.
4. **Zero trust**: любой входной параметр, файл, заголовок и ответ внешнего API считай скомпрометированным.
5. **SAST обязателен**: чтение исходников — это не опциональный шаг. Пропуск SAST допустим только если исходный код объективно недоступен (нет доступа к репозиторию/файловой системе — black-box сценарий). Отсутствие времени, большой объём кода или «код выглядит простым» — не являются основанием для пропуска. Если код недоступен, явно зафиксируй это в отчёте («SAST не проводился: код недоступен») и переходи в чистый black-box DAST-режим.
6. **DAST обязателен, если технически возможен**: если целевое приложение запущено или может быть запущено (есть команда старта, конфиг, доступный порт) — активное тестирование запущенного приложения через Playwright/agent-browser/curl **обязательно** для каждой находки, допускающей проверку без разрушительного эффекта (см. правило 2). Откладывать или пропускать DAST «на потом», ограничиваясь только чтением кода, **запрещено**.
   - Пропуск DAST для конкретной находки допустим **только** по одной из явно проверенных и задокументированных причин:
     а) приложение технически не запускается после реальной попытки (зафиксируй точную команду и ошибку запуска);
     б) пользователь явно запретил активное тестирование или ограничил скоуп только чтением кода;
     в) конкретный вектор физически не поддаётся динамической проверке без разрушительного эффекта в проде (например, необратимая массовая операция) — тогда применяется правило 2, а не общий отказ от DAST;
     г) при аудите конкретной доработки (коммита/PR) ни один изменённый файл не входит в исполняемый код или конфигурацию работающего приложения и не влияет на его поведение (допустимые исключения: только документация `*.md`/`*.txt`, комментарии, `.gitignore`/`LICENSE`, изолированные unit/e2e-тесты). По каждому изменённому файлу в отчёте приводится явное обоснование; если хотя бы один файл влияет на приложение или проводится полный аудит, причина (г) неприменима;
     д) конкретная проблема (в режиме Pentest) или требование стандарта (в режиме OWASP ASVS) по своей природе верифицируется статически, по конфигурации или по документации (`SAST` / `CFG` / `DOC` — например: захардкоженные секреты и приватные ключи в репозитории/бандле, уязвимые зависимости SCA, алгоритмы хэширования паролей, запись секретов в лог-файлы, конфигурация Dockerfile/K8s/CI), где полным и достаточным доказательством (PoC) является сам артефакт кода или конфигурации, а не HTTP-запрос.
   - Запрещено самостоятельно решать «DAST здесь не нужен» из-за субъективной уверенности в результате, лени поднимать стенд или того, что динамически проверяемая находка «выглядит очевидной» по коду. Гипотеза из SAST по динамическому вектору — это входные данные для DAST, а не замена ему.
   - Различай **статус DAST всего аудита** (в таблице `0. Покрытие проверки`) и **метод подтверждения отдельной находки**:
     * В таблице `0. Покрытие проверки` ставится `DAST = done`, если стенд был доступен и ты провёл динамические проверки (даже если динамических уязвимостей не нашлось, а все найденные проблемы оказались статическими/конфигурационными по п. `д`). Значение `DAST = skipped` во всём аудите допустимо только по общим причинам `(а/б/г)`.
     * Для отдельной находки: если это динамически проверяемый вектор, но DAST для него пропущен по причинам `(а/б/в)`, ставится `SAST-only (теоретический риск, не подтверждён DAST)` с указанием причины; если же находка относится к п. `(д)`, ставится `SAST` или `CFG` (подтверждена артефактом кода/конфигурации, без понижения до теоретического риска).
   - Перед тем как заявить о недоступности среды (причина а), обязательно предпринять попытку запуска через `webapp-testing` или использовать уже работающий экземпляр — «выглядит сложным» не считается попыткой.

## Режимы работы

Скилл поддерживает два режима:

1. **Режим Pentest (по умолчанию)** — активный поиск уязвимостей по OWASP Top 10, OWASP API Security Top 10 и продвинутым векторам. Используется всегда, когда пользователь просит «проверить безопасность», «провести пентест / аудит», «проверить по OWASP» без упоминания `ASVS`. Выполняется по Фазам 0–4 ниже.
2. **Режим OWASP ASVS (только по явному требованию)** — проверка соответствия требованиям стандарта OWASP Application Security Verification Standard.
   - Включается **исключительно по явному запросу пользователя**, где назван `ASVS` (например: «проведи аудит по OWASP ASVS L2», «проверь по ASVS, главы V6–V8»). В обычных проверках и на каждую доработку полный аудит ASVS **не запускается**. Если пользователь просит «проверить на соответствие стандарту безопасности», но не уточнил стандарт — уточни, нужен ли режим Pentest или аудит по OWASP ASVS.
   - Если пользователь запросил проверку по ASVS, но **не указал уровень (`L1`, `L2` или `L3`)**, сначала задай вопрос с кратким пояснением, какой уровень для чего предназначен (`L1` — базовая защита для систем с низким риском; `L2` — рекомендуемый уровень для большинства приложений с ПДн и бизнес-данными; `L3` — критичные системы: финансы, медицина, госсектор), и дождись ответа. Не выбирай уровень самостоятельно.
   - Источник требований в режиме ASVS: приоритет — скачанный CSV последнего стабильного релиза из `https://github.com/OWASP/ASVS/tags` через скрипт `scripts/asvs_requirements.py`; если скачать не удалось — используется приложенный файл `references/owasp-asvs.csv`.
   - Полная методика, правила статусов (`Pass` / `Fail` / `N/A` / `Not verified`) и шаблон отчёта ASVS — в `references/owasp-asvs.md`.

## Связь с другими скиллами

- Скилл `webapp-testing` — инструмент запуска приложения и автоматизации через Playwright. Используй его для поднятия серверов и браузерных действий.
- Скилл `agent-browser` — альтернативный браузерный движок, если Playwright недоступен.

## Рабочий цикл

- В режиме **Pentest (по умолчанию)** двигайся по Фазам 0–4 последовательно.
  * **Полный аудит (Full Audit):** проверяются все маршруты и модули приложения.
  * **Аудит доработки (Delta / PR Audit):** если пользователь просит проверить конкретный коммит, ветку или PR, сначала определи изменённые файлы (`git diff`) и их обратные зависимости (blast radius: какие маршруты, контроллеры, guards и шаблоны используют изменённый код). Если срабатывает правило 6(г) — задокументируй это; иначе выполни SAST и активный DAST прицельно по всем затронутым и смежным маршрутам.
- В режиме **OWASP ASVS** выполни Фазы 0–1 для сбора контекста и далее следуй регламенту и шаблону отчёта из `references/owasp-asvs.md`.

### Фаза 0. Определи поверхность атаки и целевой стенд

1. Определи стек по манифестам и структуре репозитория (`package.json`, `pyproject.toml`/`requirements.txt`, `pom.xml`/`build.gradle`, `go.mod`, `composer.json`, `Gemfile`, `*.csproj`, `Cargo.toml`): язык, бэкенд-фреймворк, SSR/фронтенд-фреймворк, ORM/драйвер БД. Сопоставь стек с матрицей конструкций в `references/attack-surface.md`.
2. Найди точки входа: порты API и фронтенда, глобальные префиксы маршрутов, конфигурацию middleware/guards/фильтров, версии API, SSR Server Actions / Route Handlers.
3. Определи наличие условных модулей, которые расширяют набор проверяемых векторов: GraphQL, WebSocket / real-time шлюзы, внешняя OAuth/OIDC/SAML/SSO-авторизация, входящие Webhooks / платёжные коллбэки, файловое хранилище с presigned URL (S3-совместимое), XML/SOAP/SVG-парсинг, серверная шаблонизация, мультитенантность (изоляция организаций/тенантов), интеграции с LLM / AI-агентами, SSR / Server Actions / BaaS (Next.js/Nuxt/Supabase и др.). Зафиксируй, какие из них есть — это определит, какие разделы `references/advanced-vectors.md` и `references/attack-surface.md` включать в Фазу 3.
4. Определи целевой стенд `{протокол}://{домен}:{порт}`: если пользователь указал URL уже развёрнутого стенда (тестовый контур, staging, prod или уже работающий локальный инстанс) — работай с ним напрямую. Если проверка локальная и приложение ещё не запущено — подними его через скилл `webapp-testing` или штатной командой запуска проекта (`npm run ...`, `uvicorn ...`, `docker compose up`, `go run ...` и т. п.).

### Фаза 1. Recon — карта эндпоинтов

Собери полную карту атакующей поверхности двумя способами одновременно:

- **Из исходников**: все объявления маршрутов/контроллеров/обработчиков, их HTTP-методы и пути; подключённые middleware/guards/фильтры авторизации и схемы валидации входных данных. Сверяйся с `references/attack-surface.md`.
- **Динамически**: пройди по приложению в браузере (Playwright/agent-browser), включи перехват запросов (`page.route`, HAR-запись), залогинься и собери фактически вызываемые эндпоинты, заголовки, форматы запросов/ответов и наличие токенов.

Составь таблицу: эндпоинт → метод → роль/доступ → входные параметры → наличие авторизации/валидации.

### Фаза 2. Threat model — приоритизация

Отранжируй цели по риску. Сначала проверяй то, что даёт максимальный эффект при минимальных затратах: публичные/мутирующие эндпоинты без авторизации, места конкатенации в запросы к БД, клиентский рендеринг пользовательских данных, исходящие запросы по пользовательским URL.

### Фаза 3. Активное тестирование по категориям

Проверяй по категориям OWASP Top 10. Для каждой категории: ищи проблему в коде (SAST) и подтверждай её эксплуатацию на запущенном приложении (DAST). Статический чек-лист по категориям (AuthN/AuthZ, инъекции, клиентская безопасность, секреты, DoS) — в `references/security-checklist.md`, разбор тест-кейсов и пейлоадов — в `references/owasp-top10.md`, готовые пейлоады — в `references/payloads.md`.

Ключевые категории:
1. **AuthN / AuthZ / IDOR (BOLA/BFLA/Cross-Tenant)** — доступ к чужим ресурсам и объектам другого тенанта по `id`/`tenantId`, отсутствие серверной проверки прав на маршруте, доверие к идентификатору пользователя из параметров запроса вместо сессии/токена, отсутствие инвалидации сессий при смене пароля и уязвимости флоу сброса пароля.
2. **Инъекции (SQL/NoSQL/Command)** — непараметризованные запросы к БД (сырой SQL с конкатенацией/интерполяцией строк), передача пользовательского ввода в вызовы командной оболочки или интерпретатора.
3. **XSS (reflected/stored/DOM)** — отключение контекстного экранирования шаблонизатора или клиентского фреймворка, небезопасная вставка в DOM, отражение ввода без кодирования.
4. **CSRF** — мутирующие запросы с cookie-аутентификацией без `SameSite`/CSRF-токена.
5. **SSRF** — исходящие запросы по пользовательскому URL/вебхуку без белого списка хостов и блокировки внутренних/метаданных IP-адресов.
6. **File upload / Path traversal / Zip Slip** — невалидированные имена и типы файлов, обход каталога через `../` при чтении/сохранении и при распаковке архивов, отдача загруженного HTML/SVG с выполнением в браузере.
7. **Misconfiguration (headers/CORS/CSP/HSTS/Cookie/Cache)** — разрешение произвольного `Origin` (включая ошибки префикса/суффикса/regex и `Origin: null`) при `credentials: true`, отсутствие `HttpOnly`/`Secure`/`SameSite` на сессионных cookie, отсутствие `CSP` (`frame-ancestors`), `HSTS`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, кеширование приватных ответов (`Cache-Control: no-store`), раскрытие stack trace.
8. **Rate limiting / DoS** — отсутствие лимитов частоты на входе/регистрации/восстановлении доступа/тяжёлых операциях, отсутствие лимитов размера тела запроса и загружаемых файлов, ReDoS.
9. **Секреты, криптография и зависимости (SCA)** — ключи, пароли и токены в исходниках, `.dockerignore`/образах и клиентском бандле; слабое хэширование паролей; уязвимые сторонние библиотеки.
10. **JWT / OAuth2 / OIDC / SSO deep-dive** — `alg=none`, RS256→HS256 key confusion, `kid`-injection, невалидируемый `redirect_uri`, отсутствие `state`/PKCE, привязка аккаунта по неподтверждённому email. Детали — `references/owasp-top10.md` и `references/advanced-vectors.md`.
11. **Business logic / race conditions (TOCTOU) / HPP / CSV Injection** — повторное использование одноразовых кодов/купонов, гонки при списании баланса/лимитов, обход шагов многошагового процесса, Mass Assignment, HTTP Parameter Pollution, инъекция формул при экспорте CSV/XLSX. Детали — `references/advanced-vectors.md`.
12. **XXE / SSTI / Десериализация / Prototype Pollution** — внешние сущности в XML/SOAP/SVG, компиляция шаблонов из пользовательской строки, небезопасная десериализация, глубокое слияние JSON-объектов в JS/TS. Детали — `references/advanced-vectors.md`.
13. **Open Redirect / Clickjacking / Cache Poisoning / Host Header** — невалидируемые редиректы, кликджекинг чувствительных действий, отравление кеша и ссылок сброса пароля через `Host`/`X-Forwarded-Host`. Детали — `references/advanced-vectors.md`.
14. **Условные модули по результатам Фазы 0** — GraphQL, WebSocket, входящие Webhooks/платёжные коллбэки, файловое хранилище/S3, мультитенантность (Cross-Tenant), интеграции с LLM/AI, SSR / Server Actions / BaaS — только если присутствуют в проекте. Детали — `references/advanced-vectors.md` и `references/attack-surface.md`.

### Фаза 4. Отчёт

Всегда структурируй отчёт строго по этому шаблону:

```markdown
### 0. Покрытие проверки
| Метод / Параметр | Статус / Значение | Комментарий |
|---|---|---|
| Режим и скоуп | Pentest (Full / Delta) | проверенные модули / ветка |
| Целевой стенд | {протокол}://{домен}:{порт} / не запускался | тип окружения (local / test / stage / prod) |
| Охват маршрутов | проверено X из Y эндпоинтов | перечень основных проверенных контуров |
| SAST | done / skipped | причина, если skipped |
| DAST | done / skipped | выполненные активные проверки или причина (а/б/г), если skipped |

### 1. Сводка аудита
| Уровень | Количество |
|---|---|
| 🔴 CRITICAL | N |
| 🟠 HIGH | N |
| 🟡 MEDIUM | N |
| 🔵 LOW | N |
| ⚪ INFO | N |

### 2. Детальный разбор находок
#### [SEVERITY] Название (CWE-XXX / OWASP)
- Файл и строки: path/to/file:NN
- Метод подтверждения: DAST-подтверждено / SAST / CFG / SAST-only (теоретический риск, причина пропуска DAST: а/б/в)
- Описание уязвимости
- Вектор атаки / доказательство (PoC-запрос и ответ для DAST; точный артефакт кода/конфигурации для SAST/CFG)
- Уязвимый фрагмент (код / конфигурация)
- Рекомендация по исправлению
```

**Критерии оценки критичности (Severity):**
- 🔴 **CRITICAL**: удалённое выполнение кода (RCE), SQLi/SSRF с доступом к БД или облачным метаданным, полный обход аутентификации, компрометация административного доступа или всех данных системы, приватные ключи/секреты production в репозитории или клиентском бандле.
- 🟠 **HIGH**: BOLA/IDOR с чтением или изменением чужих чувствительных данных или данных другого тенанта, Stored XSS, BFLA (доступ обычного пользователя к привилегированным функциям), подделка платёжных вебхуков, гонки (TOCTOU) с финансовым ущербом, CSRF на критичных действиях.
- 🟡 **MEDIUM**: Reflected/DOM XSS с дополнительными условиями, Open Redirect, CSRF на некритичных операциях, отсутствие rate limiting на аутентификации/сбросе пароля, утечка внутренней структуры в ошибках, слабая конфигурация CORS без прямого перехвата сессии.
- 🔵 **LOW**: отсутствие защитных HTTP-заголовков без подтверждённого вектора эксплуатации, перечисление пользователей (user enumeration), избыточное время жизни некритичных токенов, минорные информационные утечки.
- ⚪ **INFO**: архитектурные наблюдения, рекомендации по эшелонированной защите (defense-in-depth) и пункты, не образующие самостоятельного вектора атаки.

Раздел «0. Покрытие проверки» — обязателен всегда, независимо от результата аудита. Значение `skipped` для SAST или DAST допустимо только с указанием одной из задокументированных причин (см. правила 5 и 6 в разделе «Границы и правила») — самостоятельное решение агента «этот метод здесь не нужен» без явной причины запрещено.

Для каждой находки поле «Метод подтверждения» обязательно:
- `DAST-подтверждено` — есть воспроизводимый запрос и ответ/эффект на запущенном приложении;
- `SAST` / `CFG` — для чисто статических или конфигурационных проблем по пункту (д) правила 6 (секреты в коде, SCA, хэширование паролей, логирование, инфраструктурные конфиги);
- `SAST-only (теоретический риск)` — если проблема предполагает динамическую эксплуатацию, но DAST пропущен по одной из причин (а/б/в) с явным указанием причины и условий эксплуатации.

В режиме ASVS используй шаблон отчёта и статусы из `references/owasp-asvs.md`.

Для динамической находки всегда приводи фактический запрос (curl/Playwright-сниппет), который воспроизводит проблему, и полученный ответ/эффект. Для gray-box дополнительно указывай место в коде, где проблема возникает.

## Инструменты и приёмы

### Playwright (через скилл webapp-testing)
- `page.route()` — перехват и подмена запросов/заголовков/ответов (для проверки авторизации, подмены `Origin`, обхода CSRF).
- `page.request` / `request.get|post` — отправка «сырых» HTTP-запросов с произвольными заголовками и телом, в обход браузерных ограничений.
- `page.on('response')` — чтение кодов ответов, заголовков (`Set-Cookie`, `CSP`, `HSTS`), времени ответа (для rate limiting / timing-атак).
- HAR-запись (`page.route_from_har` / `record_har_content`) — реконструкция фактического трафика приложения.
- Запуск локального сервера (если целевой стенд `{протокол}://{домен}:{порт}` ещё не развёрнут): через скрипт `with_server.py` из скилла `webapp-testing` или штатной фоновой командой запуска стека (`npm run ...`, `uvicorn ...`, `docker compose up`, `go run ...`).

### agent-browser
- Снапшоты accessibility-дерева и компактные refs для навигации; `agent-browser skills get core` для базовых команд.
- Применяй, когда нужен интерактивный браузер с сессиями/авторизацией и перехватом трафика.

### Общие правила тестирования
- Меняй по одному параметру за раз, фиксируй эффект — иначе непонятно, что сработало.
- Сравнивай с baseline (ожидаемое поведение без атаки), чтобы отличить уязвимость от штатного поведения.
- Не гонись за полнотой в ущерб точности: лучше 3 подтверждённые находки с PoC, чем 20 бездоказательных предположений.
