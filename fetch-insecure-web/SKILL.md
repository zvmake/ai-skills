# Подключение к сайтам с нестандартным УЦ (национальным, корпоративным, тестовым)

## Обзор

Сайт подписан УЦ, которого нет в системном хранилище. Порядок действий: **определить issuer → добыть правильный CA-сертификат из надёжного источника → подключить его как доверенный только на время конкретного запроса**.

Адреса надёжных источников не угадывай — они указаны в самих сертификатах: расширения **AIA (CA Issuers)** и **CRL Distribution Points** показывают, где оператор УЦ публикует свою цепочку.

Нельзя: `-k/--insecure`, `verify=False`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, установка сертификата в системное хранилище без согласия пользователя, PEM из случайного источника. Проверка TLS остаётся включённой всегда.

## Когда применять

Ошибки доверия TLS при HTTPS-запросе: `ERR_CERT_AUTHORITY_INVALID`, `SEC_E_UNTRUSTED_ROOT`, «unable to verify the first certificate», «выпущена центром сертификации, не имеющим доверия», `schannel: the revocation status is unknown`, webfetch «Transport error» — и сайт подписан нестандартным УЦ: национальным УЦ, корпоративным/внутренним, тестовым.

Осторожно: если публичный сайт незнаком и официального источника сертификата нет — не подключай доверие молча, спроси пользователя.

## Алгоритм

1. **Диагностика** — issuer листа, полнота цепочки, где оператор УЦ публикует свою цепочку (AIA/CDP):
```bash
echo | openssl s_client -connect HOST:443 -servername HOST -showcerts 2>/dev/null > sc.txt
grep -c "BEGIN CERTIFICATE" sc.txt                                          # сколько сертификатов отдаёт сервер
awk '/BEGIN CERTIFICATE/{n++} n==1{print} /END CERTIFICATE/{if(n==1) exit}' sc.txt > leaf.pem
openssl x509 -in leaf.pem -noout -subject -issuer                           # кто лист и кто его издатель
openssl x509 -in leaf.pem -noout -text | grep -A1 -iE "CA Issuers|CRL Distribution"
```
2. **Добыть сертификат издателя листа** (кандидатов может быть несколько — см. шаг 3), по приоритету источников:
   - а) явно переданный `CA_PEM` или уже проверенный локальный PEM (кэш скрипта, файл с доверяющей машины и т.п.);
   - б) официальная публикация оператора УЦ — **адрес бери из AIA/CDP листа** (обычно каталог вида `.../cdp/` со списком файлов); можно задать `CA_URL` вручную, но не угадывай из поиска;
   - в) из цепочки самого сервера, если он её отдаёт: `bash scripts/extract-chain-ca.sh HOST 443 ca.pem`. Это доверие «первому предъявленному» (TOFU): допустимо для внутренних/тестовых ресурсов, для важных публичных сервисов предпочитай официальный источник;
   - г) с машины, где серверу уже доверяют (попросить пользователя экспортировать сертификат).

   **Как выйти на источник корневого УЦ (универсально).** AIA (CA Issuers) каждого сертификата указывает адрес сертификата его издателя — поднимайся по ступеням: лист → промежуточный → его AIA → … → пока не дойдёшь до **самоподписанного** (`subject == issuer`) — это корень.
```bash
openssl x509 -in cert.pem -noout -text | grep -A1 -i "CA Issuers"   # адрес следующей ступени вверх
openssl x509 -in root.pem -noout -subject -issuer                    # корень: subject == issuer
openssl verify -CAfile root.pem root.pem                             # ожидаемо OK (самоподписанный)
openssl verify -CAfile root.pem intermediate.pem                     # ожидаемо OK (корень подписал промежуточный)
```
   Если AIA пуст или недоступен (частый случай у внутренних/корпоративных УЦ) — смотри официальный каталог/CDP оператора, документацию УЦ или экспортируй корень с машины, где доверие уже настроено (Windows: `certutil -store Root`; Linux: `/etc/ssl/certs`).
   **Куда ставить якорь для запроса:** собери ca.pem из проверенной цепочки — **самоподписанный корень + промежуточные** (если сервер их не отдаёт, добавь в файл руками). Один промежуточный как якорь принимают не все рантаймы: curl на Windows/Schannel и `openssl ... -partial_chain` — да; node/python и curl на OpenSSL-сборках — нет (им нужен самоподписанный корень в файле). Самоподписанный лист — якорь он сам (TOFU).
3. **Выявить сертификат УЦ и проверить его** — идентифицирует не имя файла, а криптография; в каталогах операторов обычно лежат несколько поколений/ветвей с одинаковым subject и посторонние файлы (CRL/OCSP):
   - если есть адрес из AIA листа — бери файл по нему: имя может быть любым, это адрес издателя именно этого листа;
   - если AIA нет — перебери кандидатов из каталога одним циклом:
```bash
for c in candidates/*.pem; do
  openssl verify -partial_chain -CAfile "$c" leaf.pem >/dev/null 2>&1 && echo "издатель листа: $c"
done
```
   - python-эквивалент (без openssl): `ca.public_key().verify(leaf.signature, leaf.tbs_certificate_bytes, padding.PKCS1v15(), leaf.signature_hash_algorithm)` (для EC-ключей — `ec.ECDSA(leaf.signature_hash_algorithm)`);
   - сверить subject/сроки и зафиксировать SHA-256: **идентичность сертификата — отпечаток, а не имя файла**. Отпечаток изменился (ротация)? — подтверждение у пользователя;
   - Замечание: «соединение прошло» ≠ «якорь верный» — некоторые TLS-стеки (наблюдалось на Windows Schannel) принимают и неподходящий якорь; при сомнениях проверяй криптографически.
4. **Запрос с пер-запросным доверием** (проверка TLS включена):
```bash
curl -sSL --cacert ca.pem -A "<браузерный UA>" -o page.html -w "HTTP %{http_code}\n" "https://HOST/PATH"
# Windows/Schannel: «schannel: the revocation status is unknown» — приватному УЦ недоступны CRL/OCSP;
# лечится --ssl-no-revoke (снимается только проверка отзыва; цепочка проверяется). Для якоря-файла
# надёжнее всего «самоподписанный корень + промежуточные» (node/python и curl на OpenSSL-сборках —
# только так); Schannel принимает и промежуточный; при отказе — фоллбэк на OpenSSL-рантайм или корень
# в хранилище с согласия пользователя.
```
Другие рантаймы: `NODE_EXTRA_CA_CERTS=ca.pem node …`; `REQUESTS_CA_BUNDLE=ca.pem python …`; для stdlib ssl — `SSL_CERT_FILE=ca.pem`.

Быстрый старт: `bash scripts/fetch.sh <URL> [файл]` — скрипт сам добывает якорь доверия (`CA_PEM` → кэш в системном temp-каталоге, подкаталог `opencode-ca-cache` (переопределяется `CA_CACHE_DIR`) → `CA_URL` → AIA листа → цепочка сервера/самоподписанный лист), подтверждает его подписью листа, печатает использованный сертификат; **сертификаты в скилле не хранятся**, ответы HTTP ≥ 400 — ошибка (exit ≠ 0).

## Подводные камни

| Симптом | Причина / решение |
|---|---|
| webfetch «Transport error»; браузерный tool ERR_CERT_AUTHORITY_INVALID | этим каналам нельзя передать свой CA, а обходить их проверку запрещено — работай через shell + curl |
| `schannel: the revocation status is unknown` | приватному УЦ недоступны CRL/OCSP (curl на Windows/Schannel): лечится `--ssl-no-revoke` (снимает только проверку отзыва; цепочка проверяется — независимо от состава ca.pem). Состав якоря-файла: надёжнее всего «самоподписанный корень + промежуточные»; node/python и curl на OpenSSL-сборках требуют корень в файле, Schannel принимает и промежуточный; при отказе — фоллбэк на OpenSSL-рантайм (`NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`) |
| «TLS прошёл» ≠ «якорь подтверждён» | Windows Schannel может принять соединение с неподходящим якорем (наблюдалось при ротации промежуточного УЦ) — проверяй: `openssl verify -partial_chain -CAfile ca.pem leaf.pem` |
| Сервер отдаёт только лист | `extract-chain-ca.sh` не сработает: бери PEM из официального источника (адрес — в AIA/CDP) или с машины, где серверу доверяют |
| `curl` без UA → HTTP 403 «Forbidden» | некоторые сайты режут не-браузерные клиенты — добавь браузерный `-A` и `Accept-Language: ru-RU,ru;q=0.9` |

## Типичные рационализации — так не делать

| Соблазн | Реальность |
|---|---|
| «`curl -k` уже работает — оставлю так» | именно так действует агент без этого скилла (зафиксировано в тесте); `-k` отключает проверку подлинности (риск MITM). Правильный путь — `--cacert` с проверенным CA |
| «PEM проверен однажды — сойдёт навсегда» | у операторов бывают ротации промежуточных УЦ; периодически сверяй, что якорь подписывает актуальный лист |
| «Установлю CA в системное хранилище — надёжнее» | не требуется и меняет систему пользователя без его согласия; пер-запросный якорь безопаснее |
| «Возьму PEM из поиска/форума» | отпечаток не сверить; источник — официальный (адрес из AIA/CDP) или уже проверенный (вложенный) |
| «Самоподписанный — значит, можно `-k`» | для внутреннего/тестового ресурса используй TOFU-путь из алгоритма (извлечение/подтверждение), `-k` не даёт ничего, кроме потери проверки |
| «Сайт недоступен, раз webfetch вернул ошибку» | сайт доступен; ошибка про доверие, а не про доступность |

## Красные флаги — остановись и перечитай скилл

- `-k`, `--insecure`, `verify=False`, `NODE_TLS_REJECT_UNAUTHORIZED=0`
- Правка системного хранилища сертификатов без явного согласия пользователя
- CA не из официального/проверенного источника, отпечаток не сверен
- Якорь не подтверждён криптографически как подписант актуального листа
- Молчаливое подключение доверия незнакомому публичному сайту без TOFU-предупреждения

## Проверка результата

HTTP 200 и ожидаемое содержимое (санити-чек заголовка/текста), при этом ни одна команда не отключала проверку TLS.
